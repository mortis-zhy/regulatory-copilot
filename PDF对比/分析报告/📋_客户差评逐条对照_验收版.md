### 为什么 ⑥ 的 R48 必然抽错

UN R48 每个灯具编号下的**第一条永远是 §6.x.1 Presence、第二条永远是 §6.x.2 Number**。
⑥ 的抽取器按**主题名首次命中**，于是 24 条里 12 条稳定落在「配备/数量」样板上——
客户要 1200mm，拿到的是 `Presence: Mandatory`。这不是概率问题，是结构必然。

## 根因：假数据为什么会出现在 PDF 里

**是结构性问题，而且能归成一条通病：判定的粒度错了——到处用「文本长得一样吗」代替「要求是一回事吗」。**

| # | 机制 | 表现 |
|---|---|---|
| 1 | 用字符串不等当语义判定 | `oldValue !== newValue` 把 45 条**措辞差异**全判成参数变化 |
| 2 | 用主题名匹配代替条款对齐 | 按主题名首次命中 R48 → 必然落到 Presence 样板（24 条中 12 条） |
| 3 | 同一个数字有两条产生路径 | 摘要是**硬编码字面量**，账目是算出来的；硬编码那条无校验，假例子长期存活 |
| 4 | 数值与标识符同形 | `0.750`（色度值）和 `5.2.4.2`（条款号）同形，抽取器分不出，把公式尾巴报成条款号 |
| 5 | 把「抽到了非空」当「抽对了」 | MinerU 的 `markdown` 与 `tables[]` **有完全相同的串行错误**，但 `status:"verified"` 只证明抽到了文本 |
| 6 | 数据经由 markdown 中转被二次解析 | 封面参数总表用正则去刮已渲染的章节 markdown → C 列全 `—` → 48 张空卡 |
| 7 | 拿呈现形式当内容 | 比对引文文本而非数值，`N<sub>3</sub>G` vs `$\mathrm{N_3G}$` 的 markup 差异造成假「变化」 |

**为什么此前没人发现**：旧闸门只校验**内部一致性**（行数 ≥ valueDiff 数、每行有 C 引用），
没有一条校验**内容正确**。48 张占位卡照样全绿，因为它们在结构上就是「表格」。

## 防再犯：新增 6 道闸门 + 交付闸门加项

|---|---|---|

| `two-version chapters declare their scope` | 13/14 章范围声明被删 | — |
| `printed TOC page numbers resolve to real chapter pages` | 目录页码全退化成同一值 | — |
| `matrix cells that matched a number actually carry it` | 捕获组抓错片段 → 匹配成功但数值空 | — |
| `matrix covers every declared family` | 参数数或参数族被意外删减 | — |
| **交付闸门第 7 项**「参数矩阵三版覆盖」 | A<80% / B<60% / C 全空 | 清空 C 列 → 422 拒发，实测 ✅ |

**五条通用原则**（上述闸门的机械固化）：

1. **一个数据集只能有一个解析器** —— 结构化字段优先，markdown 只负责渲染，不许反向解析
2. **判等只比语义，不比呈现** —— 比 `nums`，不比引文文本
3. **空值必须带原因**，且区分「该版没有规定」与「抽取器读不出」，后者要有第二语料兜底
4. **每个对外数字只有一个来源 + 断言校验** —— 能算出来的数字不许有第二条产生路径
5. **宁可空着，不可错着** —— 定位错比定位不到更危险，读者会当真
