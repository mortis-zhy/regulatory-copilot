# 法规号更正 —— 引用错一部法规，和引用一个**不存在的法规**

**日期**：2026-11-05
**触发**：客户 DR-004（P1）、DR-005（P1）
**交付件**：`delivery/PDF对比/㊱_法规号更正_263页_2026-11-05.pdf`（263 页）
**闸门**：141 → **142**

---

## 一、两条错，都是「标准号写错了」

| 明细 | 报告原来写的 | 原文 |
|---|---|---|
| **DR-004** | R48 §5.30.1「带制造商徽标的光信号灯具应按 **UN R10** 等取得型式批准」 | 「the lamp shall be type approved according to the requirements of **the UN regulation No 148**」 |
| **DR-005** | 「C 引 **UN R4511**」 | 「according to **UN Regulation No. 45**<sup>11</sup>」 |

### DR-004：引了**另一部法规**

UN R10 是**整车型式认证**，不是灯具认证。
按报告写的 R10 去选认证依据，客户会跑错程序。

### DR-005：引了**一部不存在的法规**

原文长这样：

```
according to UN Regulation No. 45<sup>11</sup>
                  ↑ 法规号        ↑ 脚注号（第 11 号注）
```

OCR 把法规号与脚注上标**粘在一起** → 「45」+「11」= 「**4511**」。
**一个不存在的法规**被写进了交付件 —— 客户照着它去查，查不到任何东西，
更糟的是它看起来像一个正经的法规号。

---

## 二、修法：引用的标准号必须**在它所引的那一条款里**

新增 `scripts/check_clause_citations.py`，判据：

```
引用里点名的标准号 ∈ 该条款原文窗口里出现过的标准号
```

窗口 = 该版语料里，条款号出现处往后 600 字。
标准号按「前缀 + 号」归一（`UN regulation No 148` 与 `UN R148` 都算 UN148）。

检查范围是**带条款号的引用**：

1. 要求台账的登记理由（`data/requirement-gaps.json`）；
2. §11.9 定性义务清单的三版原文摘录（`data/qualitative-obligations.json`）；
3. 参数 spec 的 `why` 里点名的标准号（`data/parameter-specs.json`）。

### 两个必须踩准的坑

#### ① 脚注上标：**先摘内容，再摘标签**

```python
text = re.sub(r"<sup>.*?</sup>", "", text)   # 先摘内容
text = re.sub(r"<[^>]+>", "", text)           # 再摘标签
```

顺序反过来，「UN Regulation No. 45<sup>11</sup>」会变成
「UN Regulation No. 4511」—— **判据自己就把 OCR 的粘连当成真的**。
（`<sub>3</sub>` 这种**下标**要留着：`N<sub>3</sub>G` 是车辆类别，不是脚注。）

#### ② 条款窗口**不许找窄到查不着**

初版 `clause_window` 用「条款号后面不能跟点号」作判据。
但条款号在标题里常带尾点（「5.30.1.」）→ 整条被判成「找不到」→
**这一条静默地不查** → 闸门全绿，问题还在。

真正的判据是「后面不能跟**数字**」（避免把 5.30.1 认成 5.30.12）：

```python
re.finditer(re.escape(clause) + r"(?!\.?\d)", full_text)
```

**这是本轮最值得记的一条**：闸门的一个判据写窄了，
它就从「检查」变成了「静默跳过」——
而**跳过比报错更难发现**。

### ③ 跨版本的**说明文字**不能按单一条款核

`nature` / `designImpact` / `testImpact` 这三栏会**同时提到三版各自的标准**
（A/B 引 GB/T 21260、C 引 UN R45），拿单一条款去核它必然误报。

**要查的是「引文」**（`quote`）—— 那才是报告对外的证据。

## 三、改了什么

| 位置 | 原来 | 现在 |
|---|---|---|
| `requirement-gaps.json` C §5.30.1 | 引 UN R10 | 引 **the UN regulation No 148**（原文），并说明错在哪 |
| `qualitative-obligations.json` C 引文 | 「UN Regulation No. 4511」 | 「UN Regulation No. 45」，脚注号挪进 `c.note` |
| `parameter-specs.json` | 「UN R4511」 | 「UN R45」 |
| `parameter-specs.json` | 「GB 2019」 | 「GB 4785-2019」 |
| 报告里的说明文字 | 「OCR 把两者粘成了「UN R4511 / UN R4516」」 | 「OCR 把法规号与脚注号粘在一起（45 + 11、45 + 16），看起来像另一个法规号」 |

最后一条改动的用意：**交付件里不再出现「R4511」这个字符串**。
解释一个错误形态时把错误形态原样写出来，客户 grep 一次就会再报一次差评。

实测（重建后的报告全文）：

| 形态 | 出现次数 |
|---|---|
| `R4511` / `R4516` | **0** |
| `UN R45` | 4 |
| `UN R148` | 1 |
| `UN R10` | 1（背景引用：「配合 UN R10（整车型式认证）承载」，已登记） |

## 四、新增闸门（141 → 142）

`引用的标准号必须真的在它所引的那一条款里`

**证明它会红**：把 C §5.30.1 的理由改回「UN R10」，闸门立刻报：

```
[FAIL] requirement-gaps.json C §5.30.1：C §5.30.1 里没有「UN10」
       （该条款窗口内实际有：UN148, UN37）
```

**证明它不会静默跳过**：把 `clause_window` 的判据改回「后面不能跟点号」，
DR-004 那一条**直接消失**（不被检查）→ 闸门假绿。
这条与 2.② 是同一个教训：**判据写窄了，它就从检查变成了静默跳过。**

- 交付件里不再出现「R4511 / R4516」字符串。
