# 抽取层选型：OXR vs MinerU —— 实测结论

**日期**：2026-11-03
**目的**：换一套新法规标准要 2–3 周，其中「抽取」这段能不能更快更准？
**方法**：不用任何榜单 —— 拿**我们自己已知的坏点**当场判。
**复现**：`scripts/oxr_ab_chroma.py`（单页深挖）+ `scripts/oxr_ab_tables.py`（全样本）
**数据**：`reports/oxr-ab-chroma.json`、`reports/oxr-ab-tables.json`

---

## 〇、为什么不用榜单

OXR-1.0（SoMarkAI，2026-10-20 开源，1.3B）自报三榜第一：

| 榜单 | OXR 自报 | 竞品（同一口径） |
|---|---|---|
| OmniDocBench | **97.18** | PaddleOCR-VL-1.6 94.76 · MinerU2.5-Pro 93.42 |
| olmOCR-Bench | **87.84** | — |
| DocParsingBench | **87.76** | — |

**三个数全是开发方自己公布的，第三方独立复测一个都没有。**
而且已经有人测出榜单与真实脏表的落差：916 张真实复杂表格上，最强的解析器也只有 85.03 分（比榜单低约 10 分）。

**所以本项目的判据只有一个：拿我们的源文件 ourselves 比。**
我们恰好有一个**已知坏点** —— GB 4785-2019 的色度表，MinerU 抽它是串行的
（skill 里记着：`tables[]` 与 `markdown` 有完全相同的串行错误），只能靠源 PDF 文本层兜底。

## 一、单页深挖（色度表）

### B p17（GB 4785-2019，**已知坏点**）

源 PDF 的真实结构（按坐标重建）：

```
row27: 白色 | W12 | 绿色边界 | y=0.150+0.640x | x | y
row28: W23 | 黄绿色边界 | y=0.440
row29: W1 | 0.310 | 0.348
row31: W2 | 0.453 | 0.440
```

两个抽取器交出来的：

**MinerU（边界列串成一坨，交点列 W2–W5 全毁）**

```
| 白色 | W12绿色边界:y=0.150+0.640xW23黄绿色边界y=0.440WWWW34564561黄紫紫蓝色红色色边色边边界边界界界xxy===y000=...0530501.03008+20.750x
     | x y W1 0.310 0.348 WWWW2345 0000....455450043003 0000....443344880022 W6 0.310 0.283 |
```

**OXR（逐行逐格，rowspan 正确）**

```html
<tr><td rowspan="7">白色</td><td>W12 绿色边界 :y=0.150+0.640x</td><td>x</td><td>y</td></tr>
<tr><td>W23 黄绿色边界 y=0.440</td><td>W1</td><td>0.310 0.348</td></tr>
<tr><td>W34 黄色边界 x=0.500</td><td>W2</td><td>0.453 0.440</td></tr>
```

判定（标签与两个坐标之间**不得有别的标签**；坐标必须是完整合法的一个数）：

| | 交点（真值 27） | 边界公式（真值 19） |
|---|---|---|
| **OXR** | 抽出 27 · **对 27 · 覆盖 27/27** | 抽出 22 · 对 20 · **覆盖 19/19** |
| **MinerU** | 抽出 23 · 对 16 · **覆盖 13/27** | 抽出 24 · 对 9 · **覆盖 8/19** |

**MinerU 在这一页上，一半以上的坐标是错的，而且错得很像真的**（W1 拿到了表 2 的 0.373/0.402）。

### A p16（GB 4785 草案）—— 反过来，OXR 输了

A 的版式不同：交点列在 PDF 里**拆成 x / y 两列**。

**OXR 把 y 整列丢了**：

```html
<tr><td>W23 黄绿色边界 y=0.440</td><td>W1</td><td>0.310</td></tr>   ← 只有 x
<tr><td>W34 黄色边界 x=0.500</td><td>W2</td><td>0.453</td></tr>
```

表头是 `<td>x</td><td>y</td>`（colspan=2），数据行却只有 3 格 —— **y 整列静默消失**，
而且剩下的 0.310 **看起来完全正常**（它确实是 W1 的 x）。

同页 **MinerU 全对**：`x y W1 0.310 0.348 W2 0.453 0.440 W3 0.500 0.440 W4 0.500 0.382 W5 0.443 0.382 W6 0.310 0.283`

| | 交点（真值 10） | 边界公式（真值 9） |
|---|---|---|
| **OXR** | **覆盖 0/10** —— y 整列丢失 | 覆盖 9/9 ✓ |
| **MinerU** | **覆盖 10/10** ✓ | 覆盖 9/9 ✓ |

**两家都是「静默失败」，只是形态不同：MinerU 串行错位，OXR 丢整列。**
两种都违反本项目第一原则「宁可空着，不可错着」。

## 二、全样本（30 个表格页，通用指标）

指标不针对色度表，任何表格都能算：

- **M1 数字精确率** —— 抽到的数里有多少真在源页里出现过（查「编出来的数」）
- **M2 数字召回率** —— 源页里的数有多少被抽到（查「漏掉的数」）
- **M3 串行率** —— 一个格子里塞了 ≥3 个数的比例（串行错误的直接特征；源 PDF 每格通常 1–2 个数）
- **M4 序一致性** —— 数字序列的最长公共子序列比（抓顺序被搅乱，错位赋值躲不过）

| 版 | 抽取器 | 页数 | M1 精确率 | M2 召回率 | **M3 串行率** | M4 序一致 |
|---|---|---|---|---|---|---|
| A | MinerU | 7 | 0.857 | **0.523** | 0.155 | **0.523** |
| A | **OXR** | 7 | 0.857 | 0.488 | **0.035** | 0.408 |
| B | MinerU | 7 | 0.210 | 0.114 | 0.105 | 0.109 |
| B | **OXR** | 7 | **0.229** | **0.165** | **0.021** | 0.138 |
| C | MinerU | 16 | **0.906** | 0.672 | 0.101 | 0.662 |
| C | **OXR** | 16 | 0.874 | **0.785** | **0.055** | **0.785** |

**读法**

1. **串行率：OXR 一律更低**，约为 MinerU 的 **1/3 ～ 1/2**（A 0.035 vs 0.155 · B 0.021 vs 0.105 · C 0.055 vs 0.101）。
   这是 OXR 最实在的优势 —— 正好打在我们的已知坏点上。
2. **召回率：C 上 OXR 明显更好**（0.785 vs 0.672，R48 的表 MinerU 漏得多）；A 上略低；B 上略好。
3. **精确率基本打平**（A 0.857 = 0.857 · C 略低 0.874 vs 0.906）。
4. **B 两边都低**（0.21 / 0.23）—— GB4785-2019 的表是纯表格版式，
   而且**源 PDF 文本层本身是碎的**（`0.` + `310` 拆成两个词），基准本身就不干净。
   **这一项说明：B 的表必须人工看，工具给不出结论。**
5. **召回率普遍低于精确率**，因为分母含整页的数字（条款号、年份），不是只算表里的数。

## 三、结论

### 3.1 **不要换，要并列**

| | MinerU 4.0.6 | OXR-1.0 |
|---|---|---|
| 串行错位 | 常见 | **少 1/3～1/2** |
| 丢整列 | 少见 | **会（A p16 的 y）** |
| 我们已知的坏点 | 坏了，靠源 PDF 兜底 | 同一页全对 |
| 本机可跑 | ✓（4.0.6 已装） | ✗（要 24GB 显存起，本机是 8GB 消费卡） |
| 成本 | 0 | 免费 API（官方说别上生产）**或**租 48GB GPU |

**单独换到 OXR 会拿一个新的静默失败模式换掉旧的** —— 而且旧的已经被
「源 PDF 文本层兜底 + 107 道闸门」治住了（B p17 的串行错误从来没进过交付件，
因为 `every matrix cell's page carries the quote it shows` 那道闸门把它挡住了）。

**换抽取器会让全部 317 条 spec 的抽取结果重新洗牌**，必须整套重跑 + 逐条重核 + 重新过 107 道闸门。
**它不是一个「顺手做」的动作，是独立一轮。**

### 3.2 真正的泛化提升：**把解析器从「唯一真相」变成「三方之一」**

现在的代码是**「或」关系**：

```ts
// locate()：先试 MinerU，失败才回落到源 PDF
try { mineru } catch { sourcePdf }
```

应该改成**「核对」关系**：

```
MinerU ┐
OXR    ├─→ 三方一致 → 取值（与今天一样）
源PDF ┘        不一致 → 标「三方不一致（未判定）」+ 把三方的差异并排列出来
```

**为什么这才是重点**：两家抽取器都是**静默失败**。
- OXR 丢 y 列 → **MinerU 或源 PDF 会抓到**（那两个有 y）
- MinerU 串行 → **另外两个会抓到**（值本身没错，错的是配对）
- 三方一致 → 几乎不可能同时错

而**人工要审的量，从「全部 317 条」降到「三方不一致的那几条」**。
这才是把「换标准 2–3 周」往回压的那一刀。

### 3.3 附带的两件事

1. **MinerU 4.0.6 → 4.1.4**（昨天刚发）：新增 `advanced` 档（VLM）与
   **稳定的引用定位符 `doc:{id}/tier:{tier}/page:{page}/block:{block}`** ——
   后者能给每个取值一个**页 + 块**的锚，直接治「页码对不上」那一类错。
   **但同样属于独立一轮**（换了抽取器，spec 要重核）。
2. **OXR 的 JSON 带版面坐标**（`bbox` + `type` + `format`）——
   这让「值 → 页 → 块」可以按**几何**定位，而不是按文本检索。
   配合上面的三方对照，是把「页码对不对」变成**几何可证**的东西。

## 三之二、A/B 之外顺手挖到的两件事（**比 OXR 本身更要紧**）

做 A/B 时把「网站出的报告」和「交付给同事的报告」逐字节比了一遍，发现它们**不是同一份**。

### 3.4 仓库里有**两份抽取产物**，内容不同

| | 位置 | 入库？ | 谁用 |
|---|---|---|---|
| CLI 管线 | `dist/mineru-v4-data.json` | ✅ 已入库 | `rebuild_report.mjs`、全部闸门、交付件 |
| sidecar 管线 | `dist/sidecar-cache/*.extracted.json` | ❌ **在 .gitignore 里** | 网站的 `/api/agent/report/generate/mineru` |

**同样三份源 PDF，两份产物长度一模一样（2769868 字符），内容却不同**：

```
CLI   : \text {限值}: -1.0\% \sim -3.0\%
sidecar: \text {限值:} -1.0\% \sim -3.0\%
```

LaTeX 花括号的位置差一位 —— 是两次不同 MinerU 运行（或不同参数）的产物。

**后果**：
1. **网站出的报告 ≠ 交付给同事的报告**。差异极小（附录 A/B 的 LaTeX 花括号），
   小到内容指标都测不出来 —— 我先前比「页数 / 书签 / §11.9 / 卤素 / 塑料配光镜」全对，
   **逐字节比才发现**。
2. **新克隆跑网站会重新抽取**，得到的语料与仓库里的 CLI 语料不同 → 报告又会不一样。
3. 这正是本项目反复治的那一类病：**两份真相来源**。

**修法（很便宜）**：sidecar 的 `/extract` 在自己的缓存缺失时，
**先查仓库里已入库的 `dist/mineru-v4-data.json`** 有没有对应版本 ——
有就直接用。新上传的文件才真去抽。**一份真相来源，其余都是它的缓存。**

### 3.5 顺带说明：为什么「网站 = 交付件」这句话之前站得住

因为**代码路径是同一条**：

```ts
// server/_core/sidecarClient.ts
export async function buildSidecarReport(extracted, verified) {
  const { buildMinerUReport } = await import("../reports/reportV6");
  return await buildMinerUReport(extracted, verified);   // ← 同一个渲染器
}
```

差别**只在喂进去的语料**（3.4 那两份产物）。
所以修 3.4 之后，「网站出的」与「交付的」就真的**逐字节相同**了。

## 四、许可证（如果将来走 OXR）

- OXR 用的是 **基于 Apache-2.0 的自定义许可**（GitHub 显示 NOASSERTION，非 OSI 认证）：
  - 总融资 / 年营收 **低于 200 万美元**免费商用；超出需单独商业授权
  - **禁止提供竞品托管 API 服务**
  - 需注明在线服务来源
- MinerU 用的是自定义许可：免费商用，但 **1 亿 MAU 或月营收 2000 万美元以上**需商业授权，
  且**要求在产品里显著署名**。
- Docling 是干净的 MIT（但表格保真度最弱，且需 CPU）。

**如果这个平台将来对外做成服务，两家的许可都要先问清楚。**
内部自用没问题。
