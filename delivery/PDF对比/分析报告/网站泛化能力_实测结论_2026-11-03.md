# 网站泛化能力：实测结论

**日期**：2026-11-03
**问题**：「我们网站的泛化能力怎么样？」—— 换个新标准还能不能跑？
**方法**：不靠嘴说。拿**真实语料**跑若干种版本组合，拿机器数出来。

---

## 〇、先把「机制」与「内容」分开

| 层 | 是什么 | 换标准时 |
|---|---|---|
| **机制** | 抽取 → 矩阵构建 → 回源复核 → 渲染 → 闸门 | **不用改**（要验，见下） |
| **内容** | `data/parameter-specs.json` 这套 spec | **要重写**（这是瓶颈） |

含糊地说「换个标准也能跑」，会掩盖一个真问题：
**机制在只给两版、只给旧版、给三版时分别表现如何？**
如果机制里有写死 A/B/C 的地方，症状要等到真换标准那天才出现 —— 而那天正好最忙。

---

## 一、实测：版本组合变了会怎样

脚本 `scripts/version_subset_probe.mjs`（已进闸门）。

| 场景 | 结果 |
|---|---|
| **A/B/C（现在的配置）** | 317 行 · 951 取值位 · **796 有值**（A 284 · B 238 · C 274）· 空格 **全部有理由**（155 条已核「该版无此规定」，0 条没写原因）· 回源复核 **796/796** |
| **A/B/C + D**（第 4 版，尚未写它的 spec） | 矩阵照常构建（317 行 · 1268 位）。**D 列 0/317，整列标「未建规则」—— 有理由的空，不是静默空**；已有三版的有值数 **796 一格没变** |
| **只传 A/B**（少一版） | **响亮失败**：「spec 与语料不匹配。这份 spec 包是给【A/B/C】写的；本次上传的是【A/B】。换一套标准要另写一套 spec—— 步骤见 GENERALIZATION.md『二、换标准的操作清单』。若只是少传了一份文件，把那份补上即可。」 |
| **只传 C**（一版） | 响亮失败：「矩阵至少需要 2 版才能做对照」 |

### 这三条各自挡住了什么

- **多一版不污染老版本** —— 新版本不能改变已有版本的取值。
  「多一份真相来源」的另一种形态就是**多一个版本**；
  这一条断言把它钉住了。
- **少一版必须响亮失败** —— 把那个 throw 改成「跳过缺失的版本」看起来很合理，
  但它会把**漏传一份文件**变成一份**看起来能交付的报告**。
  这是这个项目最贵的 bug 形态，所以它进闸门。
- **空格子永远有理由** —— 不管几版，空格都必须说清是「该版确实没这条（已核）」
  还是「抽不出来」。

## 二、抽取层的质量（换标准时最该先知道的）

脚本 `scripts/table_quality.py`（已进闸门），拿源 PDF 的文本层当基准：

| 版 | 表格页 | **M1 数字精确率**（抽到的数里有多少真在源页上） | M3 串行率（一格塞了 ≥3 个数） |
|---|---|---|---|
| A 草案 | 7 | **1.000** | 0.155 |
| B 现行 | 7 | **0.364** | 0.105 |
| C UN R48-09 | 16 | **0.973** | 0.101 |

**读法**：

1. **B 版的表格抽取是坏的** —— 抽到的数里有 **64% 不在源页上**。
   交付件里的对策是「源 PDF 文本层兜底」，但那是**人工修的例外**，不是机制。
2. **串行错位（配对错）是取值级复核抓不到的一类错**：
   它的形态是「每个数都是真的，只是配错了对象」。
   实测 17 个矩阵取值取自串行格；逐个追问「它配的是哪个标签，验过吗」——
   **15 格配对已验**（标签与数值一起在源 PDF 那一页上），
   **2 格 match 就是值本身**（`'0.5 cd'`、`'2.0 Hz'`）**没有标签可配错**，
   **配对未验 0 格**。
3. 换标准时：**表格多的标准（GB 那种）必须依赖源 PDF 兜底**，
   纯 MinerU 的表格抽取不能直接用。

## 三、提议层：人工要写多少 spec

脚本 `scripts/propose_parameters.py` 自报召回（拿已有 spec 反撞候选池）：

> **召回自检：648/813 条已有 spec 的取值锚点能在候选池里找到**（**79.7%**）

- A/B 侧候选池 **593 条**（A 249 · B 196 · C 148），分好类、标好族、等人工裁定；
- C 侧另有 `scripts/propose_parameters_c.py`（274 条已有 C 模式，43 条待裁定）；
- **人工要做的事不是「从零写 813 条」，是「审 593 条候选 + 补那 20% 没被提议到的」。**
  这 20% 里既有抽取器漏的，也有「该 spec 本来就不在候选形态里」的，两类都打印出来，不藏。

> **一个自称能做参数发现的脚本，说不出自己漏了什么，那它的召回率就是个传说。**
> 所以召回自检是脚本的一部分，不是文档里的一句话。

## 四、机制里还有哪些是「内容」

| 环节 | 版本无关？ | 说明 |
|---|---|---|
| PDF 抽取（MinerU） | ✅ | 与标准无关 |
| 版本标签推断 | ✅ | 按内容指纹认，不按文件名 |
| 矩阵构建 | ✅ | 版本清单从语料推导，不是写死的 A/B/C |
| **回源复核（四档证据）** | ✅ | 引文 / 标签+取值 / 取值+条款 / 条款 |
| **串行配对复核** | ✅ | 标签与数值是否一起在源页上 |
| 渲染（HTML→PDF） | ✅ | 列数跟着语料走；三卡布局按实际版本数排 |
| 交付闸门 | ⚠️ | **要求 ≥3 版**（产品口径：客户要三版对照），不是机制限制 |
| **spec 包** | ❌ | **内容** —— 换标准要另写一套 |
| **章节→灯的映射表**（`R48_SECTIONS` 一类） | ❌ | **内容** —— 每个标准一套 |
| **定性义务清单**（`data/qualitative-obligations.json`） | ❌ | **内容** —— 人工逐条核过 |

**所以「换一套新标准要 2–3 周」这个数里，机制那部分已经压得很低了**，
剩下的是**内容**：写 spec、写映射表、核定性义务。
而内容这部分现在有**提议层**兜着（召回 79.7%），不是从零开始。

---

## 五、结论（一句话版）

> **网站的机制层已经与标准无关，而且这件事是被实测钉住的，不是声称的。**
> 真正的瓶颈是**内容**：spec 包与映射表要重写。
> 人工要写的东西，现在有提议层兜底（候选池召回 79.7%），
> 而人工要**审**的东西，从「全部 796 个取值」降到了「5 格 + 17 格配对风险（15 格已验）」。

| 问 | 答 | 证据 |
|---|---|---|
| 换个标准机制会崩吗 | 不会 | 3/4 版实测通过；少一版响亮失败；新版本不污染老版本 |
| 表格抽取能不能直接用 | **不能** | B 版精确率 0.364 |
| 人工要写多少 | spec 包要重写；提议层召回 79.7% | `propose_parameters.py` 自报 |
| 人工要审多少 | 5 格（复核分量有限）+ 17 格（串行风险，15 格配对已验） | §12.5 |
| 交付前能自动验多少 | 112 道闸门 | `npm run verify` |

## 六、还没做的（按投入产出比）

| # | 动作 | 成本 | 收益 |
|---|---|---|---|
| 1 | **把提议层的召回率固化成闸门** | 约半天 | 抽取器一变就知道提议层退化了 —— 现在只是脚本自报 |
| 2 | **OXR 接进 sidecar 当第三个投票者** | 约 2–3 天 | 串行率只有 MinerU 的 1/3～1/2；但走免费 API（官方说别上生产），且许可禁止提供竞品托管 API |
| 3 | **MinerU 4.0.6 → 4.1.4 + `doc:{id}/.../block` 定位符** | 约 1 周（要整套重跑重核） | 每个取值一个「页 + 块」锚 |
| 4 | **章节→灯映射表自动生成** | 约 1 周 | 直接砍掉「换标准」里最大的一块内容工作 |

```bash
node scripts/version_subset_probe.mjs     # 版本组合
python scripts/table_quality.py            # 表格抽取质量
python scripts/propose_parameters.py      # 提议层召回
npm run verify                             # 112 道闸门
```
