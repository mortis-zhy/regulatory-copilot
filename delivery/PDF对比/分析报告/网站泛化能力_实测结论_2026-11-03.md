# 网站泛化能力：实测结论

**日期**：2026-11-03
**问题**：「我们网站的泛化能力怎么样？」—— 换个新标准还能不能跑？
**方法**：不靠嘴说。拿**真实语料**跑若干种版本组合，拿机器数出来。

---

## 〇、先把「机制」与「内容」分开

| 层 | 是什么 | 换标准时 |
|---|---|---|
| **机制** | 抽取 → 矩阵构建 → 回源复核 → 渲染 → 闸门 | **不用改**（要验，见下） |
| **内容** | `data/parameter-specs.json` 这套 spec | **要重写**（这是瓶颈） |

含糊地说「换个标准也能跑」，会掩盖一个真问题：
**机制在只给两版、只给旧版、给三版时分别表现如何？**
如果机制里有写死 A/B/C 的地方，症状要等到真换标准那天才出现 —— 而那天正好最忙。

---

## 一、实测：版本组合变了会怎样

脚本 `scripts/version_subset_probe.mjs`（已进闸门）。

| 场景 | 结果 |
|---|---|
| **A/B/C（现在的配置）** | 317 行 · 951 取值位 · **796 有值**（A 284 · B 238 · C 274）· 空格 **全部有理由**（155 条已核「该版无此规定」，0 条没写原因）· 回源复核 **796/796** |
| **A/B/C + D**（第 4 版，尚未写它的 spec） | 矩阵照常构建（317 行 · 1268 位）。**D 列 0/317，整列标「未建规则」—— 有理由的空，不是静默空**；已有三版的有值数 **796 一格没变** |
| **只传 A/B**（少一版） | **响亮失败**：「spec 与语料不匹配。这份 spec 包是给【A/B/C】写的；本次上传的是【A/B】。换一套标准要另写一套 spec—— 步骤见 GENERALIZATION.md『二、换标准的操作清单』。若只是少传了一份文件，把那份补上即可。」 |
| **只传 C**（一版） | 响亮失败：「矩阵至少需要 2 版才能做对照」 |

### 这三条各自挡住了什么

- **多一版不污染老版本** —— 新版本不能改变已有版本的取值。
  「多一份真相来源」的另一种形态就是**多一个版本**；
  这一条断言把它钉住了。
- **少一版必须响亮失败** —— 把那个 throw 改成「跳过缺失的版本」看起来很合理，
  但它会把**漏传一份文件**变成一份**看起来能交付的报告**。
  这是这个项目最贵的 bug 形态，所以它进闸门。
- **空格子永远有理由** —— 不管几版，空格都必须说清是「该版确实没这条（已核）」
  还是「抽不出来」。

## 二、抽取层的质量（换标准时最该先知道的）

脚本 `scripts/table_quality.py`（已进闸门），拿源 PDF 的文本层当基准：

| 版 | 表格页 | **M1 数字精确率**（抽到的数里有多少真在源页上） | M3 串行率（一格塞了 ≥3 个数） |
|---|---|---|---|
| A 草案 | 7 | **1.000** | 0.155 |
| B 现行 | 7 | **0.364** | 0.105 |
| C UN R48-09 | 16 | **0.973** | 0.101 |

**读法**：

1. **B 版的表格抽取是坏的** —— 抽到的数里有 **64% 不在源页上**。
   交付件里的对策是「源 PDF 文本层兜底」，但那是**人工修的例外**，不是机制。
2. **串行错位（配对错）是取值级复核抓不到的一类错**：
   它的形态是「每个数都是真的，只是配错了对象」。
   实测 17 个矩阵取值取自串行格；逐个追问「它配的是哪个标签，验过吗」——
   **15 格配对已验**（标签与数值一起在源 PDF 那一页上），
   **2 格 match 就是值本身**（`'0.5 cd'`、`'2.0 Hz'`）**没有标签可配错**，
   **配对未验 0 格**。
3. 换标准时：**表格多的标准（GB 那种）必须依赖源 PDF 兜底**，
   纯 MinerU 的表格抽取不能直接用。

## 三、提议层：人工要写多少 spec

脚本 `scripts/propose_parameters.py` 自报召回（拿已有 spec 反撞候选池）：

> **召回自检：648/813 条已有 spec 的取值锚点能在候选池里找到**（**79.7%**）

- A/B 侧候选池 **593 条**（A 249 · B 196 · C 148），分好类、标好族、等人工裁定；
- C 侧另有 `scripts/propose_parameters_c.py`（274 条已有 C 模式，43 条待裁定）；
- **人工要做的事不是「从零写 813 条」，是「审 593 条候选 + 补那 20% 没被提议到的」。**
  这 20% 里既有抽取器漏的，也有「该 spec 本来就不在候选形态里」的，两类都打印出来，不藏。

> **一个自称能做参数发现的脚本，说不出自己漏了什么，那它的召回率就是个传说。**
> 所以召回自检是脚本的一部分，不是文档里的一句话。

## 四、机制里还有哪些是「内容」

| 环节 | 版本无关？ | 说明 |
|---|---|---|
| PDF 抽取（MinerU） | ✅ | 与标准无关 |
| 版本标签推断 | ✅ | 按内容指纹认，不按文件名 |
| 矩阵构建 | ✅ | 版本清单从语料推导，不是写死的 A/B/C |
| **回源复核（四档证据）** | ✅ | 引文 / 标签+取值 / 取值+条款 / 条款 |
| **串行配对复核** | ✅ | 标签与数值是否一起在源页上 |
| 渲染（HTML→PDF） | ✅ | 列数跟着语料走；三卡布局按实际版本数排 |
| 交付闸门 | ⚠️ | **要求 ≥3 版**（产品口径：客户要三版对照），不是机制限制 |
| **spec 包** | ❌ | **内容** —— 换标准要另写一套 |
| **章节→灯的映射表**（`R48_SECTIONS` 一类） | ❌ | **内容** —— 每个标准一套 |
| **定性义务清单**（`data/qualitative-obligations.json`） | ❌ | **内容** —— 人工逐条核过 |

### 四之二、把「内容」摊开算（2026-11-04 逐行盘点）

上面这张表只列了**三样显眼的内容**。
实际逐行盘点下来，**内容远不止三样** —— 这直接影响「换一套标准要多久」这个答复：

| # | 内容类别 | 规模 | 典型位置 |
|---|---|---|---|
| 1 | 参数 spec 正则 | 全部 813 条模式 | `data/parameter-specs.json` |
| 2 | 章节→灯映射表 | 25 条 + 名称探针 | `scripts/propose_parameters_c.py` 的 `R48_SECTIONS` —— **唯一手写处**。曾有两份拷贝（`server/_core/parameterProposals.ts` 里手抄了 25 个章节号），已改为读 `data/parameter-candidates-c.json` 的 `sections`；另加了闸门盯住。**自动生成做不到**（表里有人的判断），但已做**自动核对**：`scripts/check_section_map.py` 把每条的英文名去语料里「那一章自己的标题」对一次，24/25 一致，1 条取不到（已登记） |
| 3 | GB↔R48 章节对应表 | 28 条 | `data/r48-chapter-map.json`（人工）+ 生成产物 |
| 4 | 数据指标表 | 9 条指标 + 声称值 + 页码 | `server/reports/reportV6.ts`、`server/ingestion/indicatorScan.ts` |
| 5 | 装置类清单 / 名称别名 | 6 类 + 别名表 | `server/reports/deviceClassScan.ts`、`reportV6.ts` 的 `MATRIX_NAME_ALIAS` |
| 6 | **报告散文与提示词** | **~35 处** | `reportV6.ts` 第 11.4/12/13/14 章、`changePointChapter.ts`、`agentPrompt.ts`、`agentTools.ts`、`specAgent.ts` |
| 7 | 客户端文案 | 3 处 | `Home.tsx` 的 `GB4785_BRIEF`、`GENERIC_BRIEF`、`ReviewWorkbench.tsx` |
| 8 | 识别规则与文件路径 | ~25 处 | `python_service/main.py` 的 `DOC_SIGNATURES`、`clause_split.py` 的 `VERSION_FINGERPRINTS`、各抽取脚本里的 PDF 路径。（**版本指纹曾有两份** —— `clause_index_src.py` 自己抄了一份 if/elif，已改为引用同一处）。**2026-11-04：版本显示名表 `VERSION_META` 已独立成 `shared/versionMeta.ts`**，「表格里的版本标签怎么认」也从它派生（原来在 `typedTables.ts` 里写死了「GB 4785 草案 / … 2019 / UN R\d」），并有已知答案用例 |
| 9 | 闸门里的具体断言 | ~30 处 | `scripts/verify.mjs`（对着真实 GB 报告的章节名/表头） |
| 10 | `data/` 下的 JSON | **26 个，全部是内容** | 机制在**格式**里（按版本代号分键 + `why` + `sources` 哈希），内容要重写 |
| 11 | 死代码 | — | 已清：4 个零引用模块（1853 行）已删，并加闸门盯着 |
| 12 | **报告标题层** | 1 个声明 + 1 个组装器 | `data/standard-pack.json` + `server/reports/reportMeta.ts`。**已声明化**（2026-11-04）：换标准时改这一个 JSON，封面/章节/附录标题自动跟着语料走；闸门验「标题真的来自声明」+「声明里的标准名语料里真有」 |

> **「换标准只要重写 spec 包和映射表」这句话是不准确的** ——
> 散文、提示词、识别正则、闸门断言都是内容，而且**最容易漏**：
> 它们不像 spec 那样集中在一个文件里，散在十几个 `.ts` 里，
> 漏掉一处的症状是「报告里某句话还在讲 GB 4785」——
> **不报错，只是骗人。**

**所以「换一套新标准要 2–3 周」这个数怎么来的**：
机制那部分已经压得很低了，剩下的是上表 12 类内容。
其中第 1、2 类有**提议层**兜着（召回 79.7%），
第 3、4、5、10 类靠人工逐条核，
第 6、7、8、9 类是**改写与核对**，量大但单项都快，
第 12 类（标题层）已经**声明化** —— 改一个 JSON，不用动代码。

**盘点脚本**：`scripts/orphan_scan.mjs`（零引用模块）+
逐行 grep（写死处）。前者已进闸门。

## 五、结论（一句话版）

> **网站的机制层已经与标准无关，而且这件事是被实测钉住的，不是声称的。**
> 真正的瓶颈是**内容** —— 而且**内容不止 spec 包与映射表**：
> 散文、提示词、识别正则、闸门断言同样是内容，且最容易漏（见 §四之二）。
> 人工要写的东西，现在有提议层兜底（候选池召回 79.7%），
> 而人工要**审**的东西，从「全部 796 个取值」降到了「5 格 + 17 格配对风险（15 格已验）」。

| 问 | 答 | 证据 |
|---|---|---|
| 换个标准机制会崩吗 | 不会 | 3/4 版实测通过；少一版响亮失败；新版本不污染老版本 |
| 表格抽取能不能直接用 | **不能** | B 版精确率 0.364 |
| 人工要写多少 | **12 类内容**（不止 spec 与映射表）；提议层召回 79.7% | §四之二 + `propose_parameters.py` 自报 |
| 人工要审多少 | 5 格（复核分量有限）+ 17 格（串行风险，15 格配对已验） | §12.5 |
| **要改的具体是哪些地方** | **54 处硬编码 + 26 个数据文件**，已归成 6 条规则 + 5 组数据文件；**其中能声明化的已搬走** | **§七 / §七之二** |
| 交付前能自动验多少 | **160 道闸门** | `npm run verify` |

## 五之二、浏览器全流程实测挖出的**网站侧**缺陷（2026-11-03 晚）

上面的数据全是**管线**的。网站那一侧（真实浏览器、真下载按钮）另挖出**十个**问题
（清单与修法见 `网站全流程实测_浏览器MCP_2026-11-03.md`），其中一个是**泛化断点**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 网页文案写死「20+ 页 / 13 章 / 15-20 分钟」，且把 **MinerU 路径说成了 LLM 路径** | 读者按 15–20 分钟预留时间，实际 2 分钟；**他以为哪里出了问题** |
| 2 | 下载文件名写死「GB 4785 …」 | 换一套新标准，下载下来的 PDF **名字里还写着 GB 4785** |
| 3 | **服务端把上传的文件与生成的报告写到了 `server/uploaded-docs/`、`server/reports/`** | 那两个目录**没人读**（管线读的是仓库根）。于是 **网站上传的新标准，回源复核层根本看不见** —— 认不出它是哪一版、复核不了它的取值。**泛化断在第一步。** |
| 4 | **快速草稿会覆盖已核验的交付件**（两条管线写同一个文件） | 同事跑一次草稿，已核验的那份**从此没了** |
| 5 | **快速草稿能顶着交付件的文件名下载下来**（弹窗那条导出路没护栏） | 草稿的 PDF **内部也一模一样** —— 转发出去没人看得出它没回过源 |
| 6 | 面板抬头把 **MinerU 交付件**说成「模型逐章流式生成」 | 把**核验过的东西说成没核验**，也把没核验的说成核验过 |

第 3 条最要紧：它**没有任何报错**，而且**只在开发模式下出现**
（`path.resolve(import.meta.dirname, "../reports")` 只对打包后的布局成立）。
第 5 条是**同一个洞的第二条路**：
第 4 条修完（草稿写自己的文件）之后，护栏加在了 `/report/pdf` 上，
但**弹窗里那个「下载 PDF」按钮走的是 `/report/render`** ——
报告从客户端来，而**客户端把 `generator` 字段丢了**，服务端无从判断。
详见 `网站全流程实测_浏览器MCP_2026-11-03.md`。

修完新增**二十一道**道闸门（113 → **134**）：
网页文案不手写交付件尺寸 · 服务端路径走同一个项目根 · 下载文件名从报告派生 ·
**PDF 导出端点先判 generator 再渲染**（快速草稿不得冒充交付件导出）·
**草稿不得冒用交付件的文件名**（文件名与封面都带「未经回源复核」）·
**面板不许把交付件说成流式生成** ·
**`server/reports/` 下不许留零引用的死代码** ·
**报告不许出现语料里没有的标准** ·
**标题层必须来自声明**（且目录与正文是同一句） ·
**只许有一份报告文件与一个上传目录**（影子路径即「两份真相来源」） ·
**端口被本项目的另一个实例占着就拒绝启动**（不许静默换端口） ·
**产物必须等于重跑结果**（检查器不许写产物，见 `交付链闭合性_实测_2026-11-04.md`） ·
**报告必须记着自己是哪份上游算出来的**（上游指纹） ·
**交付件必须就是这份报告渲染出来的那份**（逐页文本比对）。

第 4–6 条是**第二轮**浏览器实测（改了前三条之后）挖出来的：
护栏加在了 `/report/pdf` 上，但**弹窗里那个「下载 PDF」按钮走的是另一条路**
（`/report/render`，报告从客户端来），**护栏没护到** ——
于是快速草稿能顶着交付件的文件名下载下来，PDF 内部也一模一样。

## 五之三、认版本：改成**按内容**认（2026-11-05）

### 1. 问题：网站那条路认版本靠的是**文件名**

项目里认版本有**三套实现**：

| 实现 | 判据 | 换标准时 |
|---|---|---|
| `python_service/main.py` 的 `DOC_SIGNATURES` | **文件名**正则 | 要改代码 |
| `scripts/clause_split.py` 的 `VERSION_FINGERPRINTS` | 内容标记 | 要改代码 |
| `server/reports/parameterMatrix.ts` 的 `loadSourceCorpus` | **内容相似度** | **不用改** |

网站那条路用的是**第一套**。实测后果：把三份源 PDF 改名成
`aaa.pdf` / `bbb.pdf` / `ccc.pdf` 再传上去 —— **整条流程在最后一步 400**
（理由是「文件名不匹配」），而**文件内容完全没问题**。
换一套标准时这一处也要改 —— 而它**本可以不用改**。

### 2. 修法：两级判据，都只看内容

`server/reports/versionRecognize.ts`：

1. **sha256 逐字节相同** —— 零歧义、零成本，最常见；
2. **内容相似度** —— 同一份标准的另一个副本。

相似度必须**同一种表示互比**：拿 MinerU 的语料文本去比 MuPDF 的上传文本，
实测只有 **0.21~0.24** —— 那是**两种排版版本**在比，判据失去区分力。
同表示互比（跨页采样）实测：

| | A | B | C |
|---|---|---|---|
| **A** | **1.000** | 0.515 | 0.142 |
| **B** | 0.515 | **1.000** | 0.158 |
| **C** | 0.142 | 0.158 | **1.000** |

同一份 1.00 / 同标准的兄弟版 0.52 / 跨标准 0.14~0.16 —— 分得很开。

> **跨页采样不是可有可无**：只看开头的话，一份**开头像**的文件就会被认成那一版 ——
> 实测把 A、B 两版各取一半拼起来，比「只看开头」时与 A 的相似度是 **1.00**，
> 等于把一份混血文件认成了 A 版。跨页采样后掉到 0.49，认不出。

### 3. 界面与链路上

- 上传完**第一秒**就显示「A 版」/「未识别」（悬停给理由），
  而不是四分钟后给一份矩阵空掉的报告；
- 两版难分时（最高分与第二名差 < 0.05）**不认** —— 宁可空着，不可错着；
- 标签一路带着 `labelSource`（content / positional）走到 sidecar：
  `content` 时**内容说了算**，文件名不同意就**说出来**（不偷偷改）；
  `positional` 时没有证据，**文件名说了算**（原来的行为）。

### 4. 顺带挖出来的一个真缺陷：网站那条路**改写了已入库的产物**

sidecar 的 `/verify` 以前会顺手把 `dist/verified-comparison.json` 写一份
（紧凑 JSON，与 `verify_claims.py` 的缩进格式不同）。于是：

- 闸门「产物与重跑结果逐字一致」下一次必红 —— 而红的原因看着像
  「产物过期了」，其实只是**格式不同**；
- 更要命的是**来源不同**：网站那条路用的抽取结果与命令行那套不是同一份来源，
  写进去的那份**未必是核验过的那份** —— 而「入库产物 = 已核验的事实」
  正是整个项目的地基。

> **症状**：在网站上点一次「生成报告」，`git status` 里
> `dist/verified-comparison.json` 变成 modified，而**没有任何人动过它**。

修法：入库的核验产物**只能由 `python verify_claims.py` 写**；
网站那条路要写，只能写缓存（gitignore 里的 `sidecar-cache`）。

### 性质要分，因为失败方式不同

|---|---|---|
| `文案` | **静默说错** —— 读者以为那是新标准的规定 | **重点盯** |
| `判据` | **响亮失败** —— 认不出新标准的文件 | 会响，次要 |
| `标识符` | 名字，一般无害 | — |

> **判据错了会响，文案错了只会骗人。**

### 三条判据（缺一条清单就会骗人）

1. **没登记的硬编码 = 红** —— 清单上没写的地方，人就不会去看；
2. **登记了但代码里已经没有了 = 红** ——
   清单里留着一项不存在的活儿，**比清单里少一项更骗人**；
3. **规则没写「为什么在这儿 / 怎么改」= 红**。

实测过三个退化场景都会红：新增一处未登记的硬编码、
规则指向了不再有硬编码的文件、规则缺 `why`。

### 闸门

`every hard-coded standard name in the source is on the swap ledger`
→ 151 项里的一项（150 → **151**）。

### 顺带：扫描器自己踩了三个坑（都写进代码注释与经验 37）

- **词法器在 JSX 上会崩**：`<div>Don't</div>` 的撇号被当成字符串开头，
  一路吞到文件末尾 —— 后面所有字面量都变成「一个巨大的字符串」。
  症状隐蔽：扫出来「有字面量」，但内容全错。**要用解析器。**
- **判据里的标准名被拆进正则里**：`GB[\s_-]*4785` 不含「GB 4785」子串 ——
  只按字面找会**整类漏掉**，而那恰恰是「认不出新文件」的那一类。

  夹在两个 `.replace()` 之间的 `//` 注释整段漏掉。

### §十三之二　换标准的**死结**已经解开（2026-11-06）

「泛化」这件事上，机制层早就换标准友好（版本清单从语料推导、认版本的判据只留一份），
但**内容层全靠人写**。这一轮把 agent-native 的**死结**解开了：

| 原来卡在哪 | 怎么解的 | 现在的状态 |
|---|---|---|
| **章号自指** —— agent 的候选句从「章里」捞，而「装置住在哪一章」是从**手写 spec 的正则**反推的。换标准 → 没有手写 spec → 推不出章号 → agent 跑不起来 → 还是得手写 spec | 章号与标题**从语料扫出来**（`data/device-chapter-map.json`，A 40 / B 33 / C 45 章），**不依赖任何手写 spec** | 装置×版本有章的：**119 → 126**；与人的背书**零冲突**；认不出的 **63 条进残余清单**，每条带能照着办的理由 |
| **校验层不看口径** —— 数值层分不出「不大于」与「小于」，于是两版口径不同却判成「一致」（客户以为不用改设计） | 校验层用抽取器**同一个** `comparatorBefore()` 算口径，并**跟同族其他版本对账** | 口径随提议一起记录；对不上就进残余，**不自动采纳** |
| **提议/判定/残余挤在一个文件里** —— 换标准时不知道哪些是「机器做完了」、哪些是「人还没看」 | 三段分离：`parameter-specs-agent.json`（提议）→ `spec-residue.json`（残余）→ `parameter-specs.json`（已采纳） | 残余**分档**（R1 机器可重试 / R2 逐条人核 / R3 不允许有）+ **上限**（30 / 16 / 0，总数 60），闸门守着 |
| **产物说不清是谁做的** —— 换个 prompt 跑出来的结果分不清、也复现不了 | 三个产物用**同一种声明**：`_generator`（脚本 @ git sha）/ `_model` / `_promptVersion` / `_sourceSha256`（源 PDF 指纹）/ `_builtAt` | 源 PDF 一换，产物**当场作废**（指纹变了） |
