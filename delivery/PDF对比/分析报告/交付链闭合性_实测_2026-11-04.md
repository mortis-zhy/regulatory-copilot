# 交付链闭合性：实测结论

**日期**：2026-11-04
**问题**：测试人员反馈「extract-cache 整个生成、保存、校验和交付链没有闭合」。
**要回答的两件事**：
① 这个说法成立吗？
② 是「API key 没接入」还是「架构」的问题？

**结论（先说）**：

> **不是 key 的问题。** `.env` 里 `MINIMAX_API_KEY` 有值，
> 而且 key 只影响**最上游那一步**（LLM 抽取）——
> 下游的 diff、复核、出报告、出 PDF **全是确定性代码**，一个 key 都不需要。
>
> **是架构的问题，而且很具体**：交付链有**三处接缝**，
> 其中**只闭合了一处**。另外两处靠「记得重跑」维持，
> **没有任何一道闸门验过「交付的那份 == 上游算出来的那份」**。

---

## 一、这条链到底长什么样

```
① 生成   extract-cache/v3-<内容哈希>.json   ← LLM 抽取（structuredExtract.ts）
            │                                    ★ 唯一需要 API key 的一步
            │  diffDocuments()（程序化，确定性）
            ▼
         diff-result.json（45 条差值）
            │  verify_claims.py（回源复核，确定性）
            ▼
         dist/verified-comparison.json + dist/facts.json
            │  buildMinerUReport（确定性）
            ▼
         reports/last-report.json
            │  renderPdfFromReportV8（确定性）
            ▼
         delivery/PDF对比/⑪_C列补全_最新版.pdf
```

| 环节 | 需要 key？ | 需要 GPU/模型？ | 可重复？ |
|---|---|---|---|
| ① LLM 抽取（extract-cache） | **要** | 否 | **不**（非确定，重跑引文会变） |
| ② 程序化 diff | 不要 | 否 | 是 |
| ③ 回源复核（verify_claims） | 不要 | 否 | 是 |
| ④ 出报告 | 不要 | 否 | 是 |
| ⑤ 出 PDF | 不要 | 否 | 是 |

> **key 只卡在第 ① 步**，而第 ① 步**故意不重跑**（改了引文）。
> 所以「key 没接」**不可能**是「链没闭合」的原因。

## 二、闭合性实测：三个实验（动手之前先做的）

每一处接缝都问同一个问题：**上游改了，下游会不会被逮住？**

### 实验 1 —— 交付件换成旧的

把 `delivery/PDF对比/⑪_...pdf` 换成 249 页的旧版（㉚）：

```
交付件页数 = 249
=== 131/131 checks passed ===
all green          ← 全绿
```

**交付件根本不在闸门的检查范围内。**
闸门默认是**自己重新渲染一遍** `reports/last-report.json` 再检查那份，
**从来不打开交付件那个文件**。
所以「改了报告、忘了重出 PDF」这条最常见的错，**没有任何一道闸门会响**。

### 实验 2 —— 改人工更正，不重建报告

把 `data/diff-corrections.json` 里一条更正的 `newValue` 改掉：

```
=== 129/131 checks passed ===
2 FAILED
  FAIL every chapter-11 diff value is backed by the source text
  FAIL the diff evidence model rejects corrections the source does not support
```

**抓到了，而且抓得正是地方** —— 差值那一半本来就有判据（取证模型逐条回原文）。

### 实验 3 —— 改 extract-cache，不重算下游

把 `dist/extract-cache/v3-….json` 里一个 topic 的条款号改掉：

```
=== 131/131 checks passed ===
all green          ← 全绿
```

**没有一条说「我是从这份缓存算出来的」。**

### 汇总

| 接缝 | 闭合？ | 依据 |
|---|---|---|
| ① 缓存 → diff-result.json | ❌ | 实验 3 全绿 |
| ② diff-result + 缓存 + 语料 → facts.json | ⚠️ **半闭合** | 见下 |
| ③ facts.json → 报告 JSON | ✅（差值那一半） | 实验 2 抓到 |
| ④ 报告 JSON → **交付件 PDF** | ❌ | 实验 1 全绿 |

> **接缝有四处，闭合的只有一处。**

### ② 为什么是「半闭合」—— 而且它比「不闭合」更隐蔽

`verify_claims.py` 会**写** `dist/verified-comparison.json` 与 `dist/facts.json`。
闸门以前**直接跑它**。

于是：**闸门每跑一次，就把这两份产物重写一遍** ——
「上游变了但产物没重算」这件事被**当场修好**，于是**永远验不出来**。

症状特别隐蔽：闸门跑完，`git status` 里 `dist/facts.json` 变成 `modified`，
而闸门**一言不发** —— 它刚把问题抹平了。

> **一个会「顺手修好」的检查器，比没有检查器更危险**：
> 它制造了一种「一切正常」的表象，而问题被它藏起来了。

## 三、补上的三道闸门

### 闸门 A：「产物 == 重跑结果」（把修复者变成检查者）

`verify_claims.py` 新增 `VERIFY_CLAIMS_OUT_DIR`；
闸门把它跑到**临时目录**，再与仓库里那两份**逐字比对**：

```
the tracked facts are what verify_claims.py produces now
  → facts.json 与 verified-comparison.json 都与重跑结果逐字一致
```

对不上就红，并告诉你按什么顺序重跑。

### 闸门 B：「报告记着自己是从哪份上游算出来的」

报告里新增 `provenance` 字段（`server/reports/provenance.ts`）：

```json
{
  "factsSha256": "640dc87c…",
  "diffResultSha256": "53a3ad5f…",
  "extractCacheSha256": { "v3-3d5ee628….json": "039c39cf…" },
  "builtAt": "2026-11-04T…"
}
```

闸门比对「报告记的」与「磁盘上现在的」：

```
the report says which upstream it was built from
  → facts/diff-result/3 份 extract-cache 的指纹都对得上
```

### 闸门 C：「交付件就是这份报告渲染出来的那份」

交付件文件名从 `render_to_pdfdir.mjs` 里读（**不另写一份**），
与闸门渲染出来的那份**逐页文本比对**：

```
the delivered PDF is the one the report renders to
  → 交付件与报告逐页一致（258 页）
```

比文本不比字节 —— PDF 里的生成时刻每次都不同。
封面那行「编制日期」是 ISO 时刻，比对前**归一化掉**；
**只抹 ISO 时刻，不抹纯日期**（正文里引用的标准发布日期是内容的一部分）。

### 三个实验的回归（同样的动作，现在会红）

| 实验 | 补闸门前 | 补闸门后 |
|---|---|---|
| ① 交付件换成 249 页旧版 | 131/131 全绿 | **红**：「交付件与当前报告对不上（258 页 vs 249 页）」 |
| ② 改人工更正 | 红（本来就有判据） | 红 |
| ③ 改 extract-cache | 131/131 全绿 | **红**：「报告是用旧的上游算出来的」 |

## 四、正确的重跑顺序（现在闸门会告诉你）

```
python verify_claims.py      # 重算事实表（产物）
node rebuild_report.mjs      # 重建报告（带 provenance）
node render_to_pdfdir.mjs    # 出交付件
npm run verify               # 闸门：产物 ↔ 上游 ↔ 交付件 三处都要对得上
```

## 五、顺带说明：客户反馈那三份文件讲的是**别的**事

测试人员给的 `对照客户之前的反馈(1).docx` / `客户反馈落实情况(1).md` / `文档问题明细.csv`
共 16 条明细（DR-001…DR-016），**没有一条提到 extract-cache**。
它们讲的是**内容**问题：

| 类别 | 例子 |
|---|---|
| 法规事实 | 6V/12V/24V 三档电压混在一行（DR-001）；750 mm 的 `<` 与 `≤` 丢失（DR-002） |
| 内部一致性 | §11.9 说 ESS 由选装变强制，第 14 章却判「无实质数值变化」（DR-003） |
| 欧标引用 | UN R148 写成 UN R10（DR-004）；UN R45 与脚注号粘连成 R4511/R4516（DR-005） |
| 翻译 | Class C (basic) passing beam 译成「基础远光」（DR-008） |
| 分析越界 | 由触发条件推导安装范围（DR-007）；「无实质数值变化 → 不需要改设计」（DR-009） |
| 覆盖面 | C 版只作参照、不参与变化判定（DR-010）；第 13 章只做 A/B（DR-011） |

**这两类是不同的工作**：
- 本文说的是**链**（产物之间有没有绑定）—— 已补三道闸门；
- 那 16 条是**内容**（结论对不对）—— 需要逐条改报告正文与 spec。

> 但两者**互相放大**：DR-001（电压档位混行）之所以能进报告，
> 是因为矩阵的取值只比「数值」、不比「**档位与条件**」——
> 那是 spec 层的问题（`data/parameter-specs.json` 的 pattern 抓得太宽）。
> 链闭合了，只能保证「报告如实反映了 facts.json」；
> **facts.json 本身对不对，仍要靠那些 spec 与人工裁定。**
