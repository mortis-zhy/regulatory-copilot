# 取值级「回源 PDF 复核」—— 设计与实测

**日期**：2026-11-03
**交付件**：`delivery/PDF对比/㉝_取值回源复核_258页_2026-11-03.pdf`（258 页）
**实现**：`server/reports/corroboration.ts`（TS，跑在矩阵构建时）
　　　　`scripts/matrix_page_check.py`（Python，独立复算）
**闸门**：110 项全绿（新增 2 项）

## 〇、问题：一句「查不到不算错」

第 12 章矩阵有 317 行 × 3 版 = 951 个取值位，其中 **796 格有值**。
交付前管这些格真实性的闸门只有一道（`scripts/matrix_page_check.py`），
它拿**引文**回源 PDF 找，找不到就归为：

> 「MinerU 与源 PDF 措辞不同，查不到不算错」

实测（2026-11-03，`matrix_page_check.py` 改造前）：

| 情况 | 格数 |
|---|---|
| 引文能在所报页上定位 | 663 |
| 引文查不到（被「不算错」放过） | **133** |

那 133 格当时**在数据里没有任何标记**，报告里也看不出它们与别的格有什么不同。

**问题出在「查不到」这个状态被合并了三件事**：

| 真实情况 | 危险程度 |
|---|---|
| 措辞不同（源 PDF 写 `'1,300'`，转写写 `'1300'`） | 无 |
| 源 PDF 的文本层把数字拆开了（`'0.'` + `'310'`） | 无 |
| **这个值根本是编出来的** | **致命** |

三者在数据里**长得一模一样** —— 表现都是「源 PDF 里找不到它」。
「不算错」等于给第三种发了一张免罪证。

> 这是本项目反复治的那一类病的一个新变种：
> **「已核」这两个字会骗人** —— 这次骗人的是「不算错」。

## 一、修法：把复核从引文层下沉到取值层

不看引文，直接看**这个值本身**在不在源 PDF 里。

### 1.1 三档证据

任一档落在**所报的那一页**上，即算定位成功：

| 档 | 证据 | 为什么算 |
|---|---|---|
| `excerpt` | 引文片段在所报页上 | 最强：读者翻过去能同时看到那句话和那个数 |
| `value+clause` | 取值字面量与条款号都在所报页上 | 人工复核时真正会看的东西：第 N 页上，第 X 条写着那个数 |
| `value` | 取值字面量在所报页上 | 引文措辞与源 PDF 不同时用（千分位 / 单位 / LaTeX） |
| `clause` | 条款号在所报页上 | 取值是英文词展开（`two minutes` → `2`） |

### 1.2 取值的写法变体

源 PDF 与转写的写法系统性不同，取值要**同时**用「字面量」与「规范化后的数值」去找：

| 转写 | 源 PDF | 候选 |
|---|---|---|
| `1300` | `1,300` / `1 300` / `1300` | 三个写法都试 |
| `0.150` | `0.150` / `0.15` | 字面量 + 规范化数值 |
| `2 0 ^`（LaTeX 拆开了数字） | `20` | 规范化数值 |
| `two minutes` | `two minutes` | 数字查不到 → 落到 `clause` 档 |

「独立的一个数」的判据：前后都不能是数字，也不能是「小数点 + 数字」
（否则 `0.15` 会命中 `0.150` 的前半截）。

### 1.3 实测结果

| 证据档 | 格数 |
|---|---|
| 引文 | **675** |
| 取值 + 条款 | **103** |
| 取值 | **18** |
| 条款 | 0 |
| **页码不符** | **0** |
| **源 PDF 全篇查不到（疑似编造）** | **0** |

**796/796 全部在所报页上找到了证据。**

133 格「引文查不到」的，全部由取值档救回 ——
它们的引文本身就是纯数值（`'1300'`、`'2 0 ^'`、`'20 ㎜'`）。

## 二、让人工只审该审的那几格

复核通过 ≠ 复核有分量。一个值如果在整份文档里到处都是
（`'3'`、`'15'`、`'20'`），「在第 72 页上找到了它」说明不了什么。

所以每格还记**该值在全文出现的页占比**。判据：
证据只有「取值」这一档、且占比 > 20% → 进「复核分量有限」清单。

**实测：5 格**（`brakeLamp.innerEdgeGapNarrow` / `directionIndicator.gapRange_1ab` /
`sideMarkerLamp` 的 4 条）。

交付件 §12.5 有这两张清单。换一套新标准时，
**人工只需要看这两张表，而不是逐条翻 796 个取值** ——
这是「换标准 2–3 周」能往回压的那一刀。

## 三、顺带抓到的：一个**静默丢列**的渲染缺陷

新表渲染出来，第 0 列（参数名）**整列不见了** ——
表还在、页还在、数字还在，只有名字没了，**而且毫无报错**。

### 根因

`server/reports/htmlRenderV8.ts` 的 `findVersionIdx` **扫了所有列**，
把「版本 / 来源 / 文档 / 文件 / 标准」这一列当成**纵向对照表**的版本列
（约定是「每行一个文档，后面几列是该文档的属性」）。

于是

```
| 参数 | 版本 | 矩阵报的页 | 取值 | 该值出现在全文 |
```

这种「**版本是某一行的属性**」的表被误判，
渲染器按版本重排后，**第 0 列被丢掉**。

`server/reports/typedTables.ts` 的 `findVersionCol` 有同样的判定。

### 修法

版本列**只在第 0 列认** —— 报告里所有合法的纵向对照表
（附录 C/D/E 的「文档 | 条款 | 页码 | 原文摘录」）版本列都在第 0 列。

### 闸门

新闸门「表格不会因版本列判定丢列」查两件事：

1. **源码级** —— 两个 `findVersion*` 判定函数只认第 0 列（根因）；
2. **PDF 级** —— 对每一张带非首列版本列的表，
   **它第 0 列的内容必须真的出现在交付件里**。

> 第 2 条才是最终判据。只查数据形状（禁止非首列版本列）会**禁止合法表形**；
> 查结果则不管渲染器怎么改都成立。
>
> 反向测试已做：把 `findVersionIdx` 改回旧行为 → 闸门立刻红。

> **「整列不见了」比「抽错一个数」更危险** ——
> 后者会被数据层的闸门抓到，前者在正文里完全看不出少了东西：
> 读者看到的是一张有页码、有取值的表，只是说不出是哪一条参数。

## 四、两套实现必须逐格一致

复核这件事有两套实现：

| 实现 | 跑在哪 | 取文本路径 |
|---|---|---|
| `server/reports/corroboration.ts` | TS，矩阵构建时 | `loadSourceCorpus` 的整页文本 |
| `scripts/matrix_page_check.py` | Python，独立复算 | `clause_split.doc_lines` 的逐行文本 |

两者走**不同的取文本路径**，所以互相独立，能当彼此的复算。

### 第一次跑：对不上，而且只看总数看不出来

| | 引文 | 取值 |
|---|---|---|
| TS | 630 | 235 |
| Python | 675 | 121 |

两边**都**判「796 格全部定位成功」，总数一致 —— 但档次分布差 45 格。

查下来是**归一化不对称**：

- 源页文本去掉了千分位逗号（`'7,000 lx'` → `'7000lx'`）；
- 引文片段**没去**（仍是 `'7,000lx.'`）。

于是引文明明在那一页上，却判成「查不到」，掉到证据更弱的取值档。

**改成两边走同一套归一化**（引文片段也去逗号、也去标记）后：
引文 675 · 取值+条款 103 · 取值 18，两套实现**逐格一致，差异 0 处**。

> **两边归一化不一致，是比规则本身更容易犯、也更难发现的错。**
> 只比总数看不出来；**逐格比**立刻就定位到是哪几格、差在哪一档。

现在新增闸门做**逐格比对**（`scripts/compare_corroboration_tiers.py`），不一致即红。
