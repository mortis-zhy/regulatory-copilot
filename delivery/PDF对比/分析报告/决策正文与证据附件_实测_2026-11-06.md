## 四、正文是**从附件生成的**，不是另写一份

这是这一版最要紧的一条设计：

```
reports/last-report.json（附件的数据）
        ↓  scripts/render_decision_brief.mjs
reports/decision-report.json（正文的数据）
        ↓  renderPdfFromReportV8
delivery/PDF对比/决策正文_最新.pdf
```

**正文里的每一个数都从附件自己的 markdown 里取**，取不到就**当场报错**：

```js
function num(label, re, text) {
  const m = text.match(re);
  if (!m) throw new Error(`决策正文取不到「${label}」—— 附件结构变了，先改这个脚本`);
  return Number(m[1]);
}
```

不填 0、不填「略」、不填上一版的数。
而且**抽完还要对数**：脚本抽了 §11.0 的表行数（必须等于清单说的条数）、
§11.9 的条目数、§12.6 的条目数 —— 对不上就抛错。

> **为什么这么严**：正文和附件是**两份文件**，最容易出的事就是
> 「附件改了、正文没重出」—— 两份文件的数对不上，
> 而**没有任何人会发现**，除非有一道闸门专门比它们。
> 这道闸门就是本版新增的那一道。

## 五、新增闸门（149 → 150）

`决策正文是 20–30 页，且每个数都跟附件一致（客户 DR-016）`
→ `scripts/verify_decision_brief.py`

盯四件事：

1. **页数在 20–30 之间** —— 短了是摘要不是正文，长了说明没拆开；
2. **正文里的 11 个关键数与附件逐项一致**（A→B 条数、台账条数、实质差异数、
   待判读数、A–C 条数、光色两数、定性义务条数、参数数、要求条数、真缺口数）；
3. **统一证据入口在**，且 7 类结论都在表里有一行；
4. **正文里没有近空白页**（客户 DR-015 提过同样的毛病）。

外加：正文的数据文件 `reports/decision-report.json` 里的数也要与附件对得上
（**证明正文是从附件生成的**，不是手写的另一份）。

### 这道闸门**咬得动**吗（两个实验）

| 实验 | 结果 |
|---|---|
| 把附件的 §11.0 条数从 22 改成 23（正文没重出） | **红**：决策正文里没有「A→B 变化条数」的当前值 ／ 正文 JSON 与附件对不上 |
| 把正文 JSON 里的 22 改成 21 | **红**：正文 JSON 与附件对不上 —— 正文不是从附件生成的 |

## 六、这一版改了什么、没改什么

**改了**：

- 新增 `scripts/render_decision_brief.mjs`（从附件生成正文）与
  `scripts/verify_decision_brief.py`（核验）；
- 新增 `reports/decision-report.json`（正文的数据，可复现）；
- 新增交付件 **决策正文（30 页）**。

**没改**：

- **证据附件一个字都没改** —— 278 页，与上一版逐字相同；
- 任何数值、任何条款号、任何页码；
- §11.0 / §11.9 / §11.10 / §12.6 / §13.x —— **均不变**。

> **两个交付件要一起给**：正文是「结论」，附件是「证据」。
> 只给正文 → 客户问「这条的依据呢」时答不上；
> 只给附件 → 就是客户说的「决策信息被原文淹没」。

---

**复现**：

```bash
node scripts/render_decision_brief.mjs        # 从附件生成决策正文

npm run verify                                # 150 道闸门
```
