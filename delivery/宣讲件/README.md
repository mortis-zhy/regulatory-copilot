## 重新生成

```bash
cd <仓库根>            # 就是本 README 所在仓库的根（不是上一级）
npm run verify          # 必须先跑 —— 讲稿里的闸门数是从这里读的
node scripts/render_briefing.mjs
```

> 讲稿输出到 `delivery/宣讲件/` —— **在仓库内**，不再写到仓库外的「工作台」目录。
> 同事克隆下来跑这一条命令，稿子就落在仓库里。

> **为什么必须先跑 verify**：讲稿里那句「N 项闸门」**不在稿子里手写**，
> 而是从 `dist/verify-summary.json` 读的（verify 每次跑完写一份）。
> 读不到就**拒绝出稿** —— 宁可空着，不可错着。
> 起因是真实踩过一次：加了一道新闸门（参数查询对空格不敏感），
> 稿子还写着旧的「97 项」，交付件里的数字与当场跑出来的结果对不上。
> `npm run verify` 里有一道闸门专门盯这件事（"讲稿里的闸门数来自机器，不是手写"）。

素材（`assets/`、`figures/`）已 gitignore —— 它们都能重新生成：

```bash
# ① 交付 PDF 的页面截图 —— **页码按内容找，不手写** ✓
#    （交付件 279 → 325 页（多了图版），手写的页码已经指错地方了 ✗）
python scripts/rebuild_briefing_shots.py
# ② 网站截图用 chrome-devtools MCP（9223 实例）截，存成 assets/w0*.png
```

> 截图脚本按**内容**找页：「核心参数 A/B/C 同框总表」「量化参数表横向对比」
> 「附录 H A/B 定性条款并排对照」「B.2.1 图版」—— 页数怎么变都不会指错 ✓。

## 两个踩过的坑（改脚本前先看）

1. **别内嵌中文字体**。四套字体 base64 后是 **97 MB 的 HTML**，
   Chromium 会在 `setContent` 阶段直接撑爆浏览器进程
   （`Target page, context or browser has been closed`）。
   宣讲稿只在本机生成，用系统字体（`Microsoft YaHei` / `SimSun`）即可。

2. **图表必须按实际显示宽度渲染**。页面可用宽度 1188 CSS px，
   图表就按 1188 渲染 —— 1:1 不缩放，字才看得清。
   早先按 1400 渲染再缩到 1188，表格里的字缩到 13px 以下，投屏根本看不清。
