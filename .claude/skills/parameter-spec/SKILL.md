# 写参数规格（parameter-spec）

> **这份 skill 跟着仓库走** —— 改 `data/parameter-specs.json` 之前请先读一遍。
> 里面每一个「坑」都是本项目**真实犯过的错**，而且写错不会报错，
> 只会安静地给出一条错的法规结论。

第 12 章三版对照矩阵的每个取值都来自 `data/parameter-specs.json` 里的一条 spec。
写错不会报错，只会**安静地给出错误的法规结论** —— 这是本项目里最贵的一类 bug。

## 核心原则

> **宁可空着，不可错着。**
> 定位不到（读者知道要自己去翻）和定位到错误（读者会当真）代价差一个数量级。

推论：**抽不到时不要放宽正则去"凑"一个值。** 宁可留空并写明原因。

## 一个 spec 的形状

```json
{
  "id": "reversing.maxHeight",
  "name": "倒车灯最大离地高度",
  "family": "安装高度 / 离地距离",
  "unit": "mm",
  "patterns": {
    "A": { "source": "5\\.21\\.4\\.2[\\s\\S]{0,220}?1\\s*400\\s*mm", "flags": "i" }
  },
  "why": { "A": "写这条正则时被什么坑过 —— 留给下一个人" }
}
```

- `patterns` 里**某版本可以留空**。留空 = 「该版确实没有规定」，与「抽取失败」在报告里措辞不同，务必区分。
- `why` 不是可选装饰。下一个改这里的人需要知道**为什么不能用更简单的写法**。

## 1–7：抽取侧的七个坑

### 1. 按条款锚定，不要按主题名

UN R48 每个灯具编号下**第一条永远是 §6.x.1 Presence、第二条永远是 §6.x.2 Number**。
按主题名首次命中，24 条里有 12 条稳定落到"配备/数量"样板 —— 客户要 1200mm，拿到 `Presence: Mandatory`。这是结构必然，不是概率。

```jsonc
// ✗ 错：主题名首次命中 = Presence 样板
"C": { "source": "reversing lamp" }
// ✓ 对：锚到定量条款
"C": { "source": "6\\.4\\.4\\.2[\\s\\S]{0,220}?1\\s*400\\s*mm" }
```

**不同版本条款号会重排。** GB4785 草案 A 的 §5.7.5.1 是垂直角，B 的 §5.7.5.1 是水平角 —— 同一编号在不同版里指不同东西，必须逐版确认。

### 2. 捕获组必须捕获「值」

`locate()` 用捕获组（若有）作为 `match`。捕获组抓错片段 → 匹配成功但数值为空。

```jsonc
// ✗ 抓到「小于」，nums 变空
"B": { "source": "车辆前行速度(小于|大于)\\s*10\\s*km" }
// ✓ 抓到值
"B": { "source": "车辆前行速度(?:小于|大于)\\s*(10\\s*km\\s*\\/\\s*h)" }
```

闸门 `matrix cells that matched a number actually carry it` 会抓到这个。

### 3. 数值与条款号同形

`0.750`（色度值）和 `5.2.4.2`（条款号）都匹配 `\d+(\.\d+){2,}`。抽取器分不出，会把隔壁公式的尾巴报成条款号。所以 `nearestClause()` 否决首位为 0 的候选 —— **你的正则如果会引入小数，别把它放在条款锚定路径上**。

### 4. UN R48 大量用英文数字

§6.5.9 原文：`within not more than one and one-half seconds by its first extinction`。
数字展开由 `numbersOf()` 负责，但你的正则**要能匹配到文字形态**：

```jsonc
"C": { "source": "within not more than one and one-half seconds by its first extinction" }
```

### 5. 只比数值，不比引文

判 A/B 是否一致时比的是 `nums`，不是引文文本。历史上按文本比，`N<sub>3</sub>G`（A 的写法）vs `$\mathrm{N_3G}$`（B 的写法）被判成"不一致"，造出一条假变化。你的正则不必为"让文本能对上"操心。

### 6. 提取路径要能落到源 PDF

MinerU 的表格抽取对 GB4785-2019 的色度表是坏的（`markdown` 与 `tables[]` 有**完全相同的**串行错误）。但源 PDF 文本层是好的 —— 只是被 PyMuPDF 拆成碎片：

```
"W12绿色边界:y=0."  "150+0."  "640x"     →  拼接后 "W12绿色边界:y=0.150+0.640x"
```

`loadSourceCorpus()` 会兜底。**能只在源 PDF 干净的文本上命中的正则，也要写进 spec** —— 本版 8 个取值靠这条路救回来的。色度类的 C 版模式锚的是英文边界名（`green boundary`），因为 LaTeX 标签 `${\mathrm{W}}_{12}$` 在正文里根本不是那个形态。

### 7. 写完必须回原文核对

```bash
node rebuild_report.mjs
python _audit2.py     # 每个取值回源 PDF 逐句核对，应为全命中（当前 176/176）
```

审计器归一化较粗：它会剥掉 HTML 标签、LaTeX 和标点再比对。**若它报"查无此句"，先确认是审计器误报还是真错** —— 这两种情况都遇到过。

## 加一个参数的流程

1. **先在源 PDF 里找到原文**，记下条款号、页码、值的写法（是 `1200mm` 还是 `1,200 mm`，R48 会不会写成 `one and one-half seconds`）
2. 在 `data/parameter-specs.json` 加一条，`family` 用已有参数族之一（`npm run verify` 会检查 9 族都在）
   —— 新参数可以从 `scripts/propose_parameters.py` 的候选池里挑，别从零想
3. `why` 写清楚**为什么不能用更简单的写法** —— 这是这个文件里最有价值的部分
4. `node rebuild_report.mjs && npm run verify`
5. `python _audit2.py` 必须仍是全命中

**也可以让 agent 先写正则，你来核对**（见 §13）：

```bash
node scripts/run_spec_agent.mjs --versions C --limit 20
```

它在 `web/参数提议确认.html` 上逐条等人采纳，服务端落盘前会用**抽取器语义**
再验一遍 —— 页面是录入界面，不是绕过校验的后门。
**它写的正则你还是要看**：实测命中率 97%，而那 3% 的失败全是「没有产出」，
不是错值 —— 但「误配量值」（抓到同章别的要求的数字）这一类，
只有人看条款号才发现得了。

## 换一套法规标准时

现有 spec **只对 GB4785 V4.3.5 / GB4785-2019 / UN R48-09 有效**，换了别的标准一条都匹配不上（交付闸门会报 `A 列仅 0/N 有取值，抽取已退化` 并 422 拒发 —— 失败是响亮的）。

不要试图靠改现有 spec 适配新标准。正确做法是**另建一套 spec 包**，复用本文件的方法，不复用它的取值。

另外三个先决条件：
- **版本清单只有一个声明处**：TS 侧 `VERSION_META`（显示名）+ `scripts/versions.py`
  （`KNOWN_VERSIONS` + `ordered_versions(docs)`）。判定层与渲染层的版本列数
  **一律从语料推导**，不许写死。
  2026-10-21 那轮把渲染层四处 `["A","B","C"]`、python 侧五处 `("A","B","C")` 全改了 ——
  改之前，**覆盖审计只审 A/B/C**：换一套标准时它的条款一条都不进账，
  而报告照样写「真缺口 0」。这是 ⑲ 事故的同构版（**「看不见」伪装成「没有缺口」**）。
  闸门 `the completeness layer is version-agnostic` 现在守着这件事。
  换标准时**不要**去改 `row.A` / `["A","B","C"]` 这类写法 —— `Row.cells` 是唯一的取值入口。
- **认不出来的 PDF 不许静默丢弃**：`scripts/clause_split.py` 的 `VERSION_FINGERPRINTS`
  是声明式指纹表；匹配不上的文件进 `UNMATCHED_DOCS` 并**打印警告** ——
  一份没进账的文件，它的条款就没人清点过，而报告照样会写「真缺口 0」。
- `loadSourceCorpus()` 用**内容指纹**（字符二元组 Dice 相似度，跨 5 个采样页）识别哪份 PDF 是哪个版本。
  不要退回按页数识别：GB 4785 草案与 2019 版封面几乎相同，只看第一页打分会打成 0.234 vs 0.233，无法区分。
- 表格自动发现不可行（73 张表里只有 13 张含数值+单位），数值参数绝大多数在**正文**里。

### 换标准后，怎么确认还「正确」

`GENERALIZATION.md`（仓库根目录）有完整清单：分三层（数据层 / 判定层 / 内容层）、
六张按版本键的人工登记表、以及要重跑的四道证据链闸门。
判据只有一条：**闸门不依赖标准是什么** —— 换完跑 `npm run verify` 就够，
不需要重新相信谁。

另外两条**换标准时最容易漏**的：

- **取证规则要在每一类数据上都有证据**。差值更正那一道闸门（`diff_value_check`）分三级：
  **数字**（值里有可用数字时）→ **逐字**（值里没有数字时，值必须逐字出现在所引条款里）
  → **锚点**（参数名/主题词必须在所引条款或所属章节里），另加**单位不冲突**检查。
  换标准后你的 spec 里一定会有**无数值的定性要求**（配备、数量、光色……），
  只写「数字对得上」的那一级，对它们**一条都查不了** —— 等于没检查，而闸门显示全绿。
- **分桶不是结论**。抽取口径的桶（「措辞差异 30 条」）回答的是「抽取时像不像差异」，
  **不能**用来下「无工程含义」这种判断。事实与过程要分开写，报告里两个口径都要标明是哪个。

### 泛化怎么测

**不能用真语料测**：硬编码与推导在三份文档的语料上结果**一模一样**。
必须喂它永远不会在生产里见到的语料 —— `_test_versions.mjs`（两版/四版/改名键）、
`_test_gen.mjs`（四版 + X/Y/Z 键名 + 缺一版）就是干这个的。
写新的泛化能力时，把「它会怎么坏」写成**合成用例**加进闸门。

## 8–12：跨版本、映射与路由侧的五个坑

### 8. 页码必须在**源 PDF**上复核

`locate()` 是在 MinerU 的分页文本上找页的，而 MinerU 的分页和源 PDF 的分页不是一回事。
写完 spec 后，除了 `_audit2.py`，还要确认这条取值在**源 PDF 的那一页**上真的存在 ——
`verify_claims.py` 的 `_pdf_page_disagrees()` 会做这一步，证伪即降级为"未核验"。
交付前实测：65 个 ✓ 里有 4 个指向的源 PDF 页面根本不含该摘录。

### 9. 车型编号不是值

「第5或第6类转向灯…不小于 350mm…不小于 500mm」「侧转向灯（5类和6类）…不大于 1800㎜」
这类句子里的 `5`、`6`、`1a` 是**编号**，不是限值。漏掉的结果不是少一个数，
而是造出一条假变化：转向信号灯垂直角曾经报成
A `2/2/1/1/1/2/2/5/15` vs B `2/1/1/1/2/2/5/15` —— 两个都是 15°，却被判为"不一致"。
`numbersOf()` 现在剥 `\d+\s*[a-z]?\s*类`。

但根因是你的正则：**用捕获组把值框住**。捕获组之外的一切（编号、交叉引用、
车辆类别）都不该进 `nums`。两条配套的写法：

```jsonc
// 双值行：locate() 只读第 1 个捕获组，所以要一个组把两个值一起框住
"A": { "source": "5\.6\.4\.2\.1[\s\S]{0,220}?(350\s*(?:mm|㎜)[\s\S]{0,80}?500\s*(?:mm|㎜))" }
// 否则 500（"其他类车辆"那一档）会静默消失
```

```jsonc
// ✗ 数值对、条款错：B 的昼间行驶灯条款里有几乎同形的「可增至2100mm」
"B": { "source": "若未安\s*装选装灯具[\s\S]{0,70}?可增至\s*(2100\s*mm)" }
// ✓ 锚到条款
"B": { "source": "5\.7\.4\.2\.1[\s\S]{0,200}?若未安…可增至\s*(2100\s*mm)" }
```

**按值锚定是最典型的假正确**：数对了、页对了、条款错了。审 spec 时不要只看数值。

### 9b. 一个条款的正文**跨页**时，条款锚点会失效 —— 用显式 `clause`

`locate()` 是**逐页扫描**的：条款号和值必须在**同一页**上，锚点才抓得到。

GB 4785-2019 的 §5.4.5.2 就是这样被 PDF 的页边界劈开的：

```
p29 尾：「…其基准轴线与车辆纵向对称平面所成角度不大52GB4785—2019」
p30 头：「于15°,即可认为满足几何可见度要求。」
```

条款号 `5.4.5.2` 在 p29，值 `15°` 在 p30 —— 锚不上。两种解法：

```jsonc
// ① 换个锚点：锚在**值那一侧**的独特短phrase上，条款号显式声明
"B": {
  "source": "于\\s*(?:\\$?\\s*\\{\\s*)?(1\\s*5)\\s*\\}?\\s*(?:\\^\\s*\\{\\s*\\\\circ\\s*\\}\\s*\\$|°)\\s*[,，]\\s*即可认为满足几何可见度要求",
  "clause": "5.4.5.2"
}
```

显式 `clause` **必须同时写 `why`**（闸门会拒）—— 下一任维护者要能判断
「这个条款号还成不成立」。

② MinerU 与源 PDF 的**写法不同**：MinerU 把 `15°` 写成 LaTeX
`${ 1 5 } ^ { \circ }$`（两个单数字），源 PDF 是干净的 `15°`。
正则要同时吃下两种；`numbersOf()` 会把 `1 5` 折回 `15`。

**值在别处也要写清 why** —— 这一条是从「条款级对照」绕回「按值锚定」，
不写理由，下一任会以为这是随手写的锚点。

### 10. 自动提议 ≠ 自动进矩阵

`scripts/propose_parameters.py` 从源文捞候选、分类、跨版本成组，并**自报召回**
（拿已有 spec 反撞候选池）。它的输出 `data/parameter-candidates.json` 是待确认清单。

确认这一步不能省，因为上面第 9 个坑就是自动生成的正则踩到的。
分组键用 **(灯具, 需求种类)**，不要用句子文本相似度 —— 全文 22 条
"离地高度不小于 Xmm"（12 种灯具）互相相似度接近 1.0，用文本分组会并成一组。

C 列走 `scripts/propose_parameters_c.py`（R48 按 §6.x.y 组织，另有一套锚定），
裁定页面在 `web/参数提议确认.html`（`/proposals`）。服务端在落盘前会用真实语料
逐条校验：必须命中、捕获组必须框出数字、命中位置必须落在所选章节区间内。

**候选表不再按"数值与 A/B 重合"过滤。** 那是个假阴性：GB 与 R48 在制动灯间距、
侧转向灯距车头这类项上本就取值不同，而"不同"正是要摆给客户看的东西。
要挡的是抓错条款，那由人核对条款号，不该由数值相等来代理。

### 11. 声明式映射表要连**名称**一起验

`R48_SECTIONS` 是一张声明式的「章节 → 灯」表。初版只验"章节号在语料里存在"，
于是 §6.14 被标成「Direction-indicator position」也照样通过 —— 而 6.14 实为
Rear retro-reflector, non-triangular。结果所有「侧转向灯」行都从回复反射器
条款里取候选句，**没有任何报错**。

现在每条带一个**名称探针**，`verify_map()` 去原文开头 1200 字里验它，
对不上就抛错；`npm run verify` 里有对应闸门（把标注改回错的，闸门即红，已实测）。

同一张表还有两个坑，都在同一次排查里暴露：

- **区间要按文档顺序切，不能按章节号排序。** 6.14 在文档里排在 6.15 之前，
  `sorted(key=int)` 会把 6.14 排到最后，于是 6.25 的区间一路吞到文末。
- **标题正则不能只写 `^6\.13\.`** —— 那会命中子条款 `6.13.4.1.`，而
  `re.search` 返回全篇第一个命中，区间起点就落在了章节中间。真实标题形态是
  `6.21. Conspicuity markings`（点后是**空格**）或被并进表格行首的 `6.14.6.14.1.`。
  要写 `^[|\s]*6\.13(?!\d)(?:\.\s|\.(?=6\.13)|\s|$)`。

### 12. 中文路由不会被 express 匹配到

`app.get("/参数提议确认.html")` 永远不触发。express 的路由比对的是 `req.path`，
即**未经解码**的 pathname，而浏览器和 curl 发的都是百分号编码形式。
症状极具欺骗性：请求落到 SPA 兜底，**返回 200 + index.html** —— 页面能开，
打开的却是另一个文档。

按解码后的路径匹配（`decodeURIComponent(req.path)`），并且 `sendFile` 失败时
显式 404，不要让它掉进 SPA 兜底。`npm run verify` 里有闸门防回退。

### 13. 条款号要**锚定**，不要「就近取号」

矩阵里每个取值都带一个条款号（客户拿它回原文核对）。旧实现是
`nearestClause(text, idx)`：扫页面文本，取**取值位置之前最近的那个条款编号**。
两种情况下错：

- **R48 把条款号印在页边栏**，正文另起一段，页边栏编号顺序与正文顺序**不一致**
  （§6.19.7 的页边栏是 3、4、5、6、2）→ 取到的是**兄弟条款**。
  后果：§6.14.4.2 的高度取值被标成 **6.14.4.6.14**（MinerU 黏表格两列的假条款号）。
- **GB 4785 草案正文里没有章号**（只有「前位灯」三个字，章号在目录里）→ 取到**上一条**。

**现在条款号取自正则开头锚定的条款字面量**：作者写 `5\.16\.4\.2`，条款号就是
5.16.4.2。`anchorClause()` 只认**三级以上**（两级是章号，`4\.0\s*±` 是数值）。

### 14. 锚对章 ≠ 锚对灯

R48 各章的措辞高度雷同（`shall not be more than 400 mm from the extreme outer edge`
在 §6.2/§6.5/§6.7/§6.9/§6.10/§6.12/§6.16 都出现）。
**锚错一章就抓错一盏灯**，而只比数值时完全看不出来：

> `sideMarkerLamp.horizontalAngle` 锚在 `5\.14\.5` —— 那是**非三角形后回复反射器**
> 的几何可见度（30°），而侧标志灯在 **5.18.5**（45°）。
> 交付件里它一度报成 30°，看着像一条实质差异，其实是取错了灯。

写完 spec 用 `python _devaudit.py` 过一遍：它拿锚定条款**所属的章**去对参数名
问的那盏灯（GB 两版的章名取**目录** —— A 的正文里没有章号；C 取正文）。
**审计脚本自己也会误报**（spec 名里带「倒车」「近光」但问的是角灯/AFS），
逐条人工核。

### 15. 取值与条款分居两页时，**显式声明**条款号

页边界会把句子劈成两半：B 的 5.16.4.2 在 p44 末尾是「…若车型结构不能保证在900mm 内,可增」，
下一行「至1500mm。」落在 p45 —— **任何单页正则都跨不过去**。
这时 spec 可以写：

```jsonc
"B": { "source": "(?:^|\n)至\s*(1500)\s*mm", "clause": "5.16.4.2",
       "why": "条款号在 p44，取值在 p45 —— 跨页，条款号显式写明" }
```

显式声明**必须同时写 why**（编译期抛错），且交付闸门会核对该条款号
**确实出现在该版原文里**（`verify.mjs` 的一条新检查）。
语料级校验放在闸门而不是构建期：构建期要能吃 `_test_versions.mjs` 的合成语料。

### 16. 单位不同写法 = 假变化

同一个门槛三种写法：GB 草案「长度大于 **6m**」、GB 2019「长度大于 **6000mm**」、
R48「length exceeding **6,000 mm**」。只比数字会判成「A/B 有变化」。

`numbersOf(text, unit)` 在 **unit === "mm"** 时把「数字 + m」换算成毫米
（只认后面不跟字母的写法：`6mm` / `12.5cm` 不动），引文仍保留原文的「6m」。
闸门的「引文必须含该取值」检查同步认这个换算 —— **不然闸门会误报**。

### 写 spec 时最常踩的四个措辞坑

- `not be more than` ≠ 原文的 **`be not more than`**（R48 §6.2.4.1 写的是后者）。
- 千分位：R48 写 `1,500`，正则写 `1500` **匹配不上**；用 `1[ ,]500`。
- GB 草案的单位是 `㎜`（U+339C）不是 `mm` —— 正则要 `(?:mm|㎜)`。
- **窗口要量**：条款号到取值的距离实测出来再写（`6.9.4.1` → `(2,100 mm` 相距 880）。
  凭感觉写的 `{0,800}` 会差几十个字符。

### 17. 批量写一族规格时：三个「每盏灯都一样」的坑

同一族的规格（三版取值相同、只有条款号不同）最适合批量写，也最容易批量写错：

- **GB 2019 有几处逐字加空格**：「对 于 离 地 高 度 小 于 750 mm」、
  「若 车 宽 小 于 1300 mm」。正则里汉字之间要 `\s*`（`小\s*于`、`不\s*大\s*于`）。
- **页边界把条款标题与正文劈开**：条款号在 p42、正文在 p43 时，任何单页正则都跨不过去。
  用**下一条款号反向锚定**：`…750\s*mm[\s\S]{0,120}?5\.18\.6`（下一条款是那盏灯独有的），
  条款号另行显式声明。
- **窗口要量**：条款号到取值的距离实测出来再写（`6.9.4.1` → `(2,100 mm` 实测 880），
  凭感觉写的 `{0,800}` 会差几十个字符。

**不锚条款就一定会撞车**：R48 各章措辞雷同，`shall not be more than 400 mm from the
extreme outer edge` 在 §6.2/6.5/6.7/6.9/6.10/6.12/6.16 都出现 ——
批次 5 里侧回复反射器 B 侧就撞上了后回复反射器的 1200mm。

### 18. 「该版无此规定」也会是假的 —— 它挡不住自己

编译期硬闸只拦得住「spec 声称某版没有这条要求，但抽取规则其实匹配上了」。
**挡不住「压根没写规则，所以标成没有」** —— 那正是把「没抽到」写成了「标准没有」。

两处真例：
- 前回复反射器垂直方向角 C 侧标着「R48 无此规定」—— R48 §6.16.5 明明写着 10°。
- 示廓灯与位置灯 200mm C 侧标着「R48 §6.13.9 全文没有」—— R48 有，
  但在 MinerU 里被排成**表格行**、行首标签还是乱的（`| 6.14.6.14.1. |`），
  按条款号检索搜不到。

**第三种：条款存在，但口径不同。**（2026-11-03 实测）
前雾灯初始下倾度的**标注精度**，GB 两版写「以不大于 **0.1%** 的精度规定」，
R48 §6.3.6.1.2.2（p46）写「shall be specified **within an accuracy of one decimal place**」。
spec 里给 C 写的 absent 理由是「R48 没有『制造商标注准确度』这一要求」——
**要求对象是同一件事，只是口径不是同一个量**，那句话是假的。
**教训**：查「这一版有没有」时，不能只按**取值**找（0.1% 在 C 里确实没有），
要按**要求**找。C 里没有 0.1%，不等于 C 没有这条要求。
**口径不同的，矩阵那一格仍然是空的**（比的是数），但 absent 理由必须写明
「C 不是没有这条要求 —— 口径不同」，并给出对方条款号。

**怎么发现**：回原文按**措辞**找一遍，不是按条款号找。
`_falseneg.py` 拿另两版的值去缺这一版的原文里找（值级线索，误报多，人工过一遍）。
**「已核」这个词很重 —— 写下它之前要真的核过。**

### 19. **假的变化比缺一个数危险得多**

一行里有两个值时，**必须用同一个捕获组把它们一起框住** ——
`locate()` 只读**第 1 个**捕获组，第二个组从来没被读过：

```jsonc
// ✗ 第二个数掉在组外 → 只剩 45
"C": { "source": "Horizontal angle:\s*(\d+)\s*°\s*inwards and (\d+)\s*°\s*outwards" }
// ✓ 一个组框住两个值 → 45 / 80
"C": { "source": "Horizontal angle:\s*(45°\s*inwards and 80°\s*outwards)" }
```

真例：`frontPositionLamp.horizontalAngle` 报成「A=45 / B=80 / C=45 → A/B 不一致」，
而三版原文写的都是「**向内 45°，向外 80°**」。三个原因叠加：
① 每版各抓了其中一个角（A 抓向内、B 抓向外、C 的第二个组没被读）；
② B 的 MinerU 文本是 LaTeX `$8 0 ^ { \circ }$`，两个正则分别落到不同的数上。

**少一个数，读者知道要自己去翻；假的变化，读者会当真。**
交付件里这一行差点让客户去改前位灯的可见度角。

### 20. LaTeX 形态取不到数 —— 只能走源 PDF

数值提取会把 `$...$` **整段剥掉**（怕把 `${N_3G}` 读成值），
所以 R48/GB2019 里写成 `$8 0 ^ { \circ }$` 的数字，**捕获组里也取不到**。

两条路：
- **源 PDF 的文本层是干净的**（PyMuPDF 拼接片段后是「向内45°,向外80°」）。
  抽取器先试 MinerU、再回落源 PDF，所以正则**只写平文本形态**即可：
  MinerU 匹配不上 → 自动回落到源 PDF（`source` 字段会记成「源 PDF」）。
- 不要在捕获组里带 `$`：整段被剥掉，值就没了。

**取不到就空着** —— 宁可这一格是「未定位到」，也不要给一个半截的值。

### 21. 条款号有四种来源，只有两种可信

| 来源 | 可信？ |
|---|---|
| 正则开头锚定的条款字面量 | ✅ 可信（作者写死的） |
| `patterns[v].clause` 显式声明（须带 why） | ✅ 可信（交付闸门核过它确实在原文里） |
| `nearestClause()` 就近推断 | ⚠️ **可能是别的条款/别的灯** |
| 空（既没锚到也没声明） | ❌ 读者无法回原文核对 |

「就近推断」出过错两次，都是**值对、条款错**：
- 转向灯低装向内角 → 推断成 4.8（那是**离地高度的测量方法**条款，原文写「测量方法参照 4.8 b)」）
- 低装灯具向下角上限 → 推断成 4.25（那是**供电电压**条款 13.5V/28V）

**这类错比抽不到更坏**：读者翻到 4.25，看到的确实是 13.5V 附近的条款，
于是**更确信**这条比对没问题，直到发现问的根本不是电压。

写完一批 spec 跑 `python _clauseaudit.py`：
②「无条款锚」= 只能靠措辞匹配的行（**人工确认没撞别的灯**），
②b「显式声明」= 抽取器直接采用的条款号。
把 ② 里的行逐个补上锚点或显式声明，② 越短越可信。

### 22. 条款号和值**不在同一页**时，锚在条款号上的正则永远匹配不到

`locate()` 一次只看一页（页与页之间有 `[第N页]` 标记，模式不能跨）。
GB 4785-2019 与 R48 里大量条款是**条款号在页尾、正文在次页**的：

- B §5.7.5.2 的 S3/S4 垂直角在 p36，条款号在 p35；
- B §5.5.5.2 的 12.5cm² 在 p33，条款号在 p32；
- C §6.5.5.1 的「inward angle of 45° may be reduced to 20°」在 p52，编号在 p51；
- A §5.9.5.2 的 12.5 ㎝² 在 p45，编号在 p44。

**症状**：正则「看起来对」，但永远命中不了，抽取结果是空的。

**改法**：按**措辞**锚（值所在页上一定有那句话），条款号**写明**：

```jsonc
// ✗ 锚在条款号上，值在次页 —— 匹配不到
"C": { "source": "6\.5\.5\.1[\s\S]{0,900}?inward angle of\s*(\d+)\s*° may be reduced to\s*(\d+)\s*°" }
// ✓ 按措辞锚 + 写明条款号
"C": { "source": "inward angle of\s*(\d+)\s*° may be reduced to\s*(\d+)\s*°", "clause": "6.5.5.1" }
```

写明条款号要写 `why`（交付闸门会查「显式声明的条款号必须在该版原文里出现过」）。
**例外**：条款号印在 PDF 左边距的**位图**里时（GB 4785 草案第 4 章就是），
文本层里根本没有这个号 —— 登记到 `data/clause-bitmap-fixes.json`（附读出依据），
闸门据此放行。

### 23. 表型要求**不要**塞进标量矩阵

限值随安装高度分档、或者写成 h 的线性公式的（近光/前雾灯的明暗截止线下倾度、
传感器的垂直探测角），压成一行数字就丢掉「哪一档对应哪个高度」——
而那恰恰是设计时唯一要用的信息。矩阵是标量表，装不下就别装；
另开附录逐字给出原文，交付闸门逐句回源验。

### 24. 审计器自己的解析缺陷会**掩盖**缺口

这一轮修覆盖审计器时，光是解析缺陷就修出三处，每一处都在藏缺口：

- `(?![\w°])` —— Python 的 `\w` **含汉字**，所以「7000lx时」「30º至60º」全都检不出来；
  单位后面只该排斥 ASCII 字母/数字：`(?![A-Za-z0-9°º])`。
- `㎝`（U+339D，SQUARE CM 单字符）不在单位表里 —— GB 草案的 12.5 ㎝² 检不到。
- 英文单位（`degree` / `lux` / `lumen` / `second`）没认 —— R48 全是英文。

**教训**：审计器要自己被审计。每修一处解析，就多认出几十条限值，也多带出几条真缺口。

## 13：取值规格提议 agent（泛化性怎么不再是天花板）

到 ㉖ 为止，第 12 章矩阵里 915 个取值位是 **788 条手写正则**跑出来的。
每一条都准（回原文核过），但它们是**泛化性的天花板**：
换一套标准、换一个版本，就要重写一遍。

现在这件事拆成三层，**只有中间一层用模型**：

| 层 | 做什么 | 用不用模型 |
|---|---|---|
| ① 候选层 | 从条款索引里把这个装置、这一版、这一族的**带数值句子**捞出来（带条款号与页码） | 不用 |
| ② 选择层 | 在候选句里挑出值，产出**条款锚定**的正则 | 用 |
| ③ 校验层 | 用**抽取器完全相同的语义**跑一遍：命中？捕获组框到值了？落在对的章？ | 不用 |

**① 和 ③ 是泛化性的关键** —— 它们不知道「近光灯最大离地高度」是什么，
只知道「这个装置的章里有带数字的句子」。换标准要改的只有
「哪个装置对应哪一章」那一张映射表（`data/r48-chapter-map.json` 那种）。

### 装置 → 章：从已有正则**反推**，不另建映射表

`deviceChapterPrefixes(specs, device, version)`：同一个 id 前缀的兄弟参数里，
凡是在这一版有正则的，它的条款号前两段就是这个装置在这一版的章
（GB 是「5.13 示廓灯」，R48 是「6.13 End-outline marker」，都是两段）。

**只保留占多数的章，并且名字对不上的一律不算** ——
同一个前缀里偶尔混进一条别的灯的规格：

- `dippedBeam.offRoadHeightOnly` 的中文名其实是「前雾灯越野车型放宽高度」，
  锚在 A 5.4.4.2 / B 5.3.4.2 / C 6.3.4.2 —— 前雾灯的章；
- `manoeuvringLamp.autoOnSpeedMax` 的中文名其实是「慢行灯自动点亮的的车速上限」，
  锚在**慢行灯**的章（GB-2019 §5.25）—— 而 GB 里根本没有「操纵灯」这个装置。

第二条在实测里造成了 agent 的**唯一一次误配量值**：
候选层把慢行灯的条文端给了「操纵灯」，agent 老老实实答了慢行灯的 10 km/h。

所以派生章号时有**两道闸**：
① `dominantDeviceToken()` —— 取这个前缀下多数规格共有的中文名（「操纵灯」「近光灯」），
   **名字不含它的规格一律不算**；
② 只保留**占多数**的章。

**归错前缀的规格要改名**（`manoeuvringLamp.autoOnSpeedMax` → `slowMovingLamp.autoOnSpeedMax`）。
取值、条款、页码本来都对，只是 id 前缀错了 —— 但前缀是机器认装置的唯一依据。

### ③ 校验层必须**逐字复用**抽取器的实现

`locate()` 是**按页扫描**的：它一页一页试，**第一个命中的页就是结果**。
所以一条正则如果在更早的别的章也能命中，抽取器就会取出错的值 ——
「值对、条款错」是这里最贵的一类 bug。

校验层因此必须复刻「第一页命中」这个语义，而不是「能不能在全文命中」。
现在它复刻的是 `paginate()` + `numbersOf()` + `nearestClause()` —— 同一份代码，
不为第二套实现。**不要在这里重写一遍归一化。**

### agent 自己能验：给它一个 `test_regex` 工具

模型写完正则，调 `test_regex` 把它放到真实语料上跑一遍，
拿回「抽取器会取到的值 / 条款号 / 页码 / 没过的理由」，不过就改。

**这一条把命中率从 58% 提到 92%** —— 失败的五条全是「窗口太短 / `[^.]`
在小数点处断掉 / 千分位逗号没写 / 区间没放进同一个捕获组」，
而这四类错误模型**自己跑一遍就知道**。

再加两处，命中率到 **97%（29/30）**：

- **思考预算给足**（`SPEC_AGENT_MAX_TOKENS`，默认 40000）。MiniMax-M3 会先输出
  一整段 `<think>`，而**思考与答案共用 max_tokens** —— 8192 不够时模型思考完就被截断，
  JSON 根本没输出。症状是「没有产出正则」，**不是错值**。
- **收口轮追问一句**「不要再调工具了，直接输出最终 JSON」。收口轮不发 `tools` 字段，
  但 MiniMax 仍可能吐工具标记；不追问这一轮就白跑。

### 写进 prompt 的硬规矩（都是踩出来的）

1. **窗口要给足**（`[\s\S]{0,900}?` 或更大）。抽取器逐页匹配，
   窗口大**不会**误命中（下一页上没有这个锚点）。
2. **不要用 `[^.]` 排除小数点** —— `[^.]*?` 会在 "2.0 Hz" 处断掉。
3. **字面量必须与候选句逐字一致**（含 LaTeX：`$\beta$` 就写 `\$\beta\$`）。
4. **条款锚点与值之间允许有别的字**，用窗口连接。
5. **区间值放进同一个捕获组**（抽取器只读第 1 个捕获组）。
6. **千分位逗号**：原文 "1,000" 要写 `1[ ,]?000`。
7. **找到数字 ≠ 找到了这个参数的量值**。同一章里常有数**别的要求**的数字：
   R48 §6.1.9.1 的「shall not exceed 100」是**参考值**，不是 GB 的
   「同时点亮远光灯最大发光强度之和」；R48 §6.3.6.1 的「-1.0 per cent」
   是**截止线倾斜度限值**，不是 GB 的「制造商标注准确度」。
   遇到这种要判「该版没有这个参数的要求」。

第 7 条加上之前，agent 在「该版无此规定」的槽位上有 2/4 抓到了同章的别的量值；
加上之后是 **0** —— 它改口说「没有」了。**宁可空着，不可错着**。

### 怎么用

```bash
# 提议（缺规则的槽位；已登记「该版无此规定」的不会被再提）
node scripts/run_spec_agent.mjs --versions C --limit 20

# 回归：把已知答案藏起来，让 agent 自己重新找一遍
node scripts/run_spec_agent_regression.mjs --sample 30
```

回归分两段，**第二段比第一段要紧**：

- **命中率**：藏起手写正则，agent 重新找，比对条款号 / 页码 / 值。
- **空槽复核**：在**人工核过「该版确实没有这条规定」**的槽位上，
  agent 要是给出一个值，那就是**编造法规**。
  报告把「误配量值」（数是真的、量值不是同一个）与「凭空生成」（数不存在）
  分开报 —— 两者的后果不同，混在一起会掩盖真正的问题。

结果记在 `reports/spec-agent-baseline.json`（**记账，不是闸门** ——
它调模型、会花钱、会有抖动）。闸门里的是 `_test_spec_agent.mjs`
（假模型，29 项检查，零成本）。

### 落盘仍然要人点头

agent 的提议写进 `data/parameter-specs-agent.json`（**提议**，不是 spec），
在 `web/参数提议确认.html` 上逐条看、逐条采纳。
服务端落盘前会**再用抽取器语义验一遍**，不过就拒 ——
页面是录入界面，不是绕过校验的后门。
